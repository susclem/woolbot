# 🐑 羊毛机器人

把「今天 10 点京东超市满 99 减 50 要领券」这种话（或者一张活动截图）发给微信机器人，
它自动理成结构化活动存进 SQLite；之后问它「今天抢什么」「周二 9 点半抢什么」，
它按你问的时间把对应活动发回来；另有一个网页日历可以总览和手动改。

- **录入**：自然语言 / 截图 → 标题、平台、开抢时刻、有效期、链接、备注
- **查询**：精确到分钟（问「11:00 抢什么」就只给 11:00 那一刻开抢的，再补一句当天
  还没开始的）；「本周六抢什么」「明天 8:30 抢什么」「今天十五点抢什么」这类**固定
  句式不经过 AI 模型**，Python 直接查库，秒回
- **帮助**：微信里发「使用帮助」直接回（不走模型）；页面右上角也有「使用帮助」，
  两边同一段字（按钮和弹窗标题都不带表情符号 —— 用户 2026-10-07 说「这个“?”表情删掉」，
  又说弹窗标题上那个也删）
- **通道**：微信 ClawBot（个人号协议），跑在飞牛 NAS 上，服务端不需要公网 IP / 域名 / 备案
- **日历**：零依赖的前端页面，月视图（左边小日历 + 右边标题清单，点标题就地看详情）+
  列表视图，能增删改、能标完成，白天/夜间两套配色（左上角那个 ☀️/🌙 按钮切）
- **模型**：任何 OpenAI 兼容接口都能换（DeepSeek / OpenAI / 本地 Ollama…）

## 三十秒上手

```bash
git clone https://github.com/susclem/woolbot.git
cd woolbot
python -m venv .venv && . .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp config.example.json config.json               # 再填一把 API key（或放 .env 里的 WOOLBOT_API_KEY）
python main.py check                             # 自检：时区、数据库、模型连不连得上
python tools/seed_demo.py                        # 塞几条演示数据，方便看前端
python main.py web                               # 打开提示的网址就能看到日历
```

- 需要一个 **OpenAI 兼容**的接口：DeepSeek、OpenAI、本地 Ollama 都行，改 `config.json` 的
  `base_url` / `model` 即可。**不需要公网 IP、域名或备案。**
- 微信通道是**可选**的：`python main.py web` 只跑网页；`python main.py all` 才连微信（扫码登录）。
- 演示数据不想要了：`python tools/seed_demo.py --wipe`。

## 数据是怎么流的

```
微信消息 / 截图                      网页日历（web/）
      │                                    │
      ▼                                    ▼
app/wechat.py  收下              app/web.py  /api/*
      │                                    │
      └────────────► app/pipeline.py ◄─────┘    ← 「这句话是要干嘛」只在这一个地方判断
                          │
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
     app/llm.py      app/repeat.py     app/db.py
   抽取 / 截图识别   重复规则与次数     SQLite（唯一的数据源）
```

关键取舍：**固定的查询句式（「明天 8:30 抢什么」「今天抢什么」）由 Python 直接查库，
一次模型都不调**；只有截图、大白话、非标准句式才交给模型解析 —— 所以它秒回、也省钱。

## 一、它长什么样

```
你：10点京东超市满99减50，限会员要先领券，有效期到今天23:59
🐑 记下了 1 条：
   🎯 10:00 开抢  京东超市 满99减50
      京东 · 限会员要先领券

你：今天抢什么
🐑 🗓 10月6日 周二 共 3 条开抢：
   09:30
   淘宝百亿补贴 秒杀
   10:00
   京东超市 满99减50
   20:00
   拼多多百亿补贴 整点抢

   **心之所向，素履以往。**

你：10点01分抢什么
🐑 📭 10月6日 周二 10:01 没有开抢安排。

   📌 10月6日 周二还没开始的 1 条：
      20:00  拼多多百亿补贴 整点抢

你：删除梦享
🐑 🗑 找到 1 条带「梦享」的活动：

   1. 云闪付 乐园门票梦享券 满1000减120  <#24>
      云闪付 · 🎯 每周五 12:00（下一次 3天后（周五））

   回复编号就删（比如「1」，或「1 2」一起删）；回复「都删」全删，回复「取消」不删。

你：1
🐑 🗑 已删掉 1 条：
      云闪付 乐园门票梦享券 满1000减120
   库里还剩 2 条。问一句「今天抢什么」就能查。
```

删东西一定要**先列出来、等你回编号**：说一句「删除临沂」不会当场删掉任何东西。

（上面每条回复末尾其实还各有一句「一言」，为了不占地方只留了第一处 —— 见下文
「每条回复的最后还有一句一言」。）

「严格只匹配那一分钟」是刻意的：你问 10:01，10:00 那条就不算命中。

**没有就是没有**。用户 2026-10-07 的原话：「我问今天的活动，为什么要把后面的给带出来，
没有就结束就行了啊」—— 回复到「📭 … 没有开抢安排。」（或「没有活动记录。」）就结束，
后面几天的活动不在这里兜底。想看往后的日子有专门的指令 `/即将`。

这一节有上限，也是在真机上撞出来的：最多列 `query.later_limit`（没写就用
`query.ongoing_limit`，默认 5）条，超出的折成「还有 N 条，去日历页面看」
——真机上它一次列过 **8 条长标题**，微信里整屏都是它。

**已经开抢过去的、只能领不能抢的一律不带**（用户原话：「不要带出今天不能抢的
活动」）。这是 2026-10-07 用户点名改的：早先那一节叫「还能领的」，问「9点半抢什么」
却把 9:00、10:00 那些**已经过去了**的和「美团全天领券」这种**只能领不能抢**的
一屏抖出来 —— 而「抢券」抢的是第一分钟，对他没用。现在只剩一种附加信息：
晚于他问的那一刻、也晚于此刻的「还没开始的」。

「今天有什么活动」那条路（`_render_day`）**照旧**带「还能领的」一节：那是看全天的
清单，把还在有效期内的券藏起来反而会让人以为没得领。按分钟问和看全天，本来就是
两个问题。

精确到分钟也要认**重复型活动展开出来的那一次**。库里「每天 08:30」只有一行、日期还停在
最初录入的那天，SQL 按时刻比是比不上的 —— 于是「明天 8:30 抢什么」会说不出来，
可同一句「明天抢什么」却明明白白列着 08:30（真机上就是这么自相矛盾的）。
现在按天取一遍、拿展开后的时刻对齐（`_rows_opening_at`）。

**主清单只列「当天开抢的」**。这个区分是 2026-10 才补上的：早先把「当天开抢」
和「当天还在有效期内」混为一谈，于是一张有效期到年底的券会在**每一天**都出现
在「今天抢什么」里，行首却写着明年才结束的日期 —— 用户第一眼只看到「共 N 条」。
现在「还能领的」另起一节，问一整周也不会把同一条刷七遍。

**清单按时刻分组**（2026-10-07 用户点名要的排版）：同一个时刻只写一遍，标题摆在该时刻
下面、缩进 3 空格 ——

```
🗓 10月7日 周三 共 6 条开抢：
   08:30
   港城欢乐购·中国银行信用卡满1000元减50元券
   港城欢乐购 工商银行信用卡满50元减10元券
   09:00
   云闪付临沂金融助力交通银行满100元减10元券
```

排序按**时刻**（`_list_lines` 先按时刻排、再分组），不是按 `list_range` 给的顺序：重复型那一
行的 `grab_at` 还停在最初录入的那天，照它排会把同一个时刻拆成两组。排序**只按时刻、且是
稳定的**：同一个时刻里的几条保持库里的先后（你录入的顺序），不按标题重排；没有时刻的
（`??:??`）排在最后。

时刻是真的**加粗**，不是 markdown：微信只收纯文本，`**08:30**` 在手机上会原样显示星号，
所以 `bold_time()` 把时刻换成数学粗体数字（U+1D7CE..U+1D7D7，`𝟎𝟖:𝟑𝟎`）。哪台手机的字库
缺这个区段（显示成方框）时，把 `app/pipeline.py` 的 `_BOLD_DIGITS` 换成 `"0123456789"`
就退回普通数字，其余代码一行都不用动。

**每条回复的最后还有一句「一言」**（`http://v1.hitokoto.cn/`，代码在 `app/sayings.py`），
与正文隔一个空行。用户 2026-10-07 的原话是「机器人每次回复都脚本请求一次一言的接口……
放在每次回复的最后面，与原回复分隔一行，用\*\*加粗」，所以那句是照他写的原样用 `**…**`
包起来的 —— 中文句子没有数学粗体字形（那招只对数字有效），微信又不认 markdown，
于是**那两个星号会实打实显示出来**。这一点问过他，他选的就是「照写」。

他给的是 `https://`，代码里默认走 `http://` 同一个域名 —— 这也是量出来的：容器里同一条连接
连打 6 次（`probe_sayings6.sh`），https 只成 **3/6**（成功那三次平均 5.87 秒，其余 8 秒读超时），
http **6/6**、平均 2.62 秒。公开玩笑接口的内容不值得为 TLS 牺牲「每条回复都带一句」。
（`app/sayings.py` 的 `HITOKOTO_URL` 是接口地址那一个开关，想换回 https 改这个常量。）

**开关在设置页上**（用户 2026-10-07 要求：「把一言的开关放进前端设置里面」）：设置弹窗里
「每条回复末尾带一句『一言』」，**默认开**（原来就只有环境变量，改一次要 SSH 进 NAS）。
关掉之后不只是不贴那句话 —— `Sayings.prefetch()` 也会立刻停手，一句都不再往那个接口发
（否则 `ClawBot` 启动时那次预取照跑，等于「关了还在偷请求」）。两层优先级：
`WOOLBOT_NO_SAYINGS=1`（部署时的硬开关）> 页面开关（`settings.sayings_enabled()`，
没设过 = 开）。它和「允许机器人闲聊」的默认值**故意相反**：一言是点名的需求，装完就该有；
闲聊是他明确不要的，装完就没有。

它只在 `app/wechat.py::handle_inbound` 发送前贴上去，`app/pipeline.py` 完全不掺和 ——
几百个流水线用例不该因为「回一条消息」就去连外网（测试里一律注入 `sayings.NoSayings()`）。

**源本身也能在页面上换**（用户 2026-10-09 贴了一言官方的分类表，要求在设置里加自定义源）。
设置弹窗里那个「一言来源」框**留空就是默认四类** `d,i,k,h`（文学、诗词、哲学、影视）；
想挑分类就填字母（逗号、空格、顿号都认，大小写都认、重复只算一次），比如 `i,k`；
想换一家就直接填一个 `http://` 或 `https://` 开头的完整网址（原样用）。这串东西
**只有 `app/sayings.py::source_url()` 一个地方解释** —— 设置页、测试、以后新加的调用方
都走它；两处各解析一次，迟早会出现「设置里显示 d,i,k,h、实际却按别的分类取」这种事。

分类字母是拼成**重复的 `c=`**（`?c=d&c=i&c=k&c=h`）发出去的。一言官方文档写的是逗号
（`?c=d,i,k,h`），但真机上那个写法**只回 400**（`{"status":400,"message":"很抱歉，没有
分类有句子符合长度区间。"}`），`?c=d%2Ci%2Ck%2Ch`、`?c=d,i` 也一样 —— 只有重复参数
是好的，照它连打 10 次拿到 `{k:2, i:3, d:2, h:2}` 四类混着出（探针 `_probe_raw.sh`）。
填了不认的字母（比如 `d,j`：`j` 是网易云，官方表里有、用户给的清单里没有，所以**故意
没加**）**当场 400 报错**并把可选的列出来，绝不悄悄丢掉 —— 用户以为设了 `d,j`、实际只按
`d` 取，这种安静的错误比报错难查一百倍。

**开抢提醒也带这句**（用户 2026-10-09 要的：「给『活动开抢前主动发微信提醒』的内容里也
加上跟机器人回复内容相同格式的『一言』，并且受设置里面的『一言』统一控制」）。做法是
`app/reminder.py::Reminder.sayings_tail()` 去拿**机器人自己那个** `Sayings` 实例
（`client.sayings`）—— 同一个池子、同一条连接、同一个开关。**没有第二个实现**：
如果提醒自己 new 一个 `Sayings()`，就会出现「两边各自请求、各自算开关、池子还不共享」，
而开关那层正是用户点名要「统一」的那个东西。取不到（或对面根本没有 `sayings`）就只是
这条不带，提醒照发。

**为什么不是「回复的时候现场请求一次」**：这个接口在国内时快时慢 —— 真机上连打 5 次
（`probe_sayings3.sh`）量到 0.65 秒、2.5 秒、5.2 秒，还有 8~9 秒直接超时的。现场请求的话
每一条回复都得陪着等这几秒（本来秒回的快路问句会明显变卡），而收发是单线程的，等它的
时候后面的消息也进不来。所以改成 `app/sayings.py` 里的**提前取好**：

- `tail()` 从池子里拿一句，**拿完立刻在后台补下一句**（池子最多囤 `POOL`＝2 句）——
  回复本身不等网络。
- 后台那次是**一口气补满池子**再停（一条回复只补一句的话，下一条回复经常还是空的），
  并且**复用同一条 `requests.Session`**（真机上每次重建 TLS 要多花 1.5 秒：TCP 0.27s、
  TLS 1.47s、之后 GET 只要 0.88s，见 `probe_sayings2.sh`）；取不到就停手，不对着打不通的接口连打。
- 池子空的那一次（比如容器刚起来、或上一句刚被用掉）才现场取一回，而且**只等
  `WAIT`＝1.5 秒**；等不到就这条不带，回复照发。
- `ClawBot` 启动时先 `prefetch()` 一句，所以第一条回复通常也已经有得用。
- 平均仍然是**一次回复一次请求**，只是发在「上一条回复之后」，不是卡在回复里。

`TIMEOUT`＝8 秒是后台那次的上限（反正在后台等）。取不到 / 超时 / 不是 JSON / 字段没了，
一律只是「这次没有这句」+ 一条 warning；贴的时候外面还另有一层 `try`（彩蛋出问题不许
弄丢正文）。哪天不想要了：设置页上那一格（`app/settings.py` 的 `sayings_enabled`），
或者容器环境变量 `WOOLBOT_NO_SAYINGS=1`（更硬，页面开不回来），都不用改代码。

## 二、跑起来

### 本机（先不碰微信）

```bash
pip install -r requirements.txt
python main.py check          # 自检：时区、数据库、模型连通性（key 在页面上填过也算数）
```

### 页面版式（月视图）

一屏两栏：**左边是月历（宽度封顶 660px，不再铺满整屏），右边是选中那天的活动标题清单**。
用户 2026-10-07 的原话是「日历小一点，日历不要占据整个屏，日历一侧显示活动标题，点击
标题进入活动详情」。

- 格子里只放两个数字：**「几号」大字在左上，「几条」小字在右下**。时刻和标题一律在
  右栏 —— 用户先让我把日历做小，然后说「把日历上的时间去掉，只保留日期右上角的活动
  数量小数字」，紧接着又说「挪到右下角吧，现在看着有点眼花。把日历上的日期数字大一点，
  日历上的数量数字小一点」（`test_the_month_view_is_a_calendar_beside_a_list` 里那条
  `_font_px` 断言盯着「日期字号 > 数量字号」，条数也不再套橙色胶囊）。想扫「哪天忙」
  看那个小数字，想知道「几点抢、抢哪个」点那天。
- 格子里还多一行小字（左下）和一个小标（右上）：**农历/节气/节日只显示一条**
  （优先级 节气 > 节日 > 农历日，农历初一显示「九月」这样的月名），**法定节假日的
  「休/班」**是个小色标（休＝红、班＝灰）。用户 2026-10-07：「给日历视图加入农历、
  二十四节气、中国节日、法定节假日」。鼠标悬停格子能看到完整一行（几号 + 农历 +

- 右栏标题按时刻分组（和微信同一个规矩：同一个时刻只写一遍，`_time_group_lines` 那套

- `?id=25` 直接把某条活动的详情摊开（和 `?settings=1`、`?help=1` 一样，方便发链接，

### 白天 / 夜间

页面有两套配色，默认跟随系统，点左上角那个按钮就自己定死，选择记在 `localStorage`
的 `woolbot_theme` 里。用户 2026-10-09：「增加"白天/夜间"切换功能，白天为现在的配色，
夜间为深色配色，把原来左上角显示"羊毛日历"的四个字去掉，增加一个切换白天夜间的按钮，
按钮显示随模式变换"☼/☽"符号」。（符号当天又换过一次，见下面第一条。）

- **按钮上那两个符号是 `☀️` / `🌙`，不是最初说的 `☼` / `☽`**（2026-10-09 用户点名
  「切换模式按钮的月亮符号换成"🌙"，太阳符号换成"☀️"」）。差别不只是好不好看：
  `☼`/`☽` 是单色字形，会跟着 `color: var(--muted)` 一起变灰；`☀️`/`🌙` 是彩色 emoji，
  颜色由系统字体决定、CSS 管不着，而它们比同字号文字更宽，所以 `.theme-toggle` 的
  `min-width` 从 40px 提到了 46px，否则符号会贴着边框。测试里反向盯着这两个老符号
  不许回来 —— 两版混用会让按钮切换时忽大忽小忽明忽暗。
- **模式的唯一权威是 `<html data-theme="light|dark">`**，由 `index.html` 里一段内联
  脚本在样式表**之前**定下来。放到 `app.js` 里就晚了：那个脚本是放在 `</body>` 前、
  **没有 `defer`** 的普通脚本，浏览器把它之前的页面解析完、往往已经画过一帧了，
  深色用户会先看到一帧白底再翻黑。所以 `style.css` 里那套深色配色从
  `@media (prefers-color-scheme: dark)` 挪进了 `:root[data-theme="dark"]` ——
  **一个媒体查询是按钮管不动的**：用户点了「白天」，但系统还是深色，媒体查询照样
  把它压回黑底。
- 系统偏好只在**没自己点过**的时候算数（`themeIsSaved()` 决定 `watchSystemTheme()`
  跟不跟随），点过之后就不再被系统改回去。
- 符号写的是**当前**模式（白天 ☀️、夜间 🌙），不是「点下去会变成什么」—— 两种读法都
  说得通，所以 `title`/`aria-label` 里把动作写明白（「切换到夜间模式」）。按钮的初始
  符号由 `paintTheme()` 在 `init()` 里刷一遍，**不写死在 HTML 上**：模式已经被内联
  脚本改过了，HTML 里写死就会和实际模式对不上。
- `:root` 里补了 `color-scheme`，两套配色各一份值。不写的话滚动条、下拉框、日期
  选择器还是按系统那套画，深色页面上就挂着一条白滚动条。
- 两套配色的变量名**必须一一对应**，`test_the_top_bar_swaps_the_title_for_a_day_night_switch`
  里那条集合比较就是盯这个的：少写一个不会报错，只会让那一处悄悄留着白天的颜色。
  唯一的例外是 `--radius`（圆角尺寸，不是颜色，一套通用）。
- `.login-qr img` 的 `background: #fff` **故意不跟着翻**：二维码要白底才好扫。
  `.btn.danger` 原来写死的 `#b91c1c`/`#f0b4b4` 深色下对比度很差，顺手换成
  `--danger` / `--danger-line` 两个变量（白天取值一模一样，浅色下没有任何变化）。

### 农历与法定节假日

格子里那行小字来自 `app/lunar.py`（**纯标准库**，不新增依赖 —— 容器是
`python:3.12-slim` 且不装系统包，为一个「今天农历几号」引一个带编译环境的库不划算）。
页面调 `GET /api/calendar?from=&to=` 拿回来，一个日子一条：

```json
{"2026-10-08": {"lunar": "八月廿八", "lunar_full": "八月廿八", "term": "寒露",
                "festival": "", "holiday": "", "text": "寒露", "kind": "term"}}
```

- **`text` 就是格子里显示的那一条**，优先级 节气 > 节日 > 农历日（同一天既是节气又是
  节日时，比如 2026-04-05「清明」+「清明节」，只写节气）。`kind` 是它的类别，页面据
  它上色（节气青、节日橙）。`holiday` 单独给「休」/「班」小标，不占 `text`。
- 页面按 **42 格网格的首尾**去取这段（`visibleRange()` 回来的 `calFrom`/`calTo`），
  不是用活动列表那个 ±7 天的区间：网格尾巴最长能伸到下个月 14 天（28 天的二月并且
  1 号正好是周一），用活动区间末尾几格就只剩一个孤零零的几号（真机截图里撞到过，
  现在 `test_the_month_view_is_a_calendar_beside_a_list` 盯着 `calFrom`）。
- 农历/节气用一张 **1900–2099 的紧凑表**（`app/_lunar_tables.py`，9KB：200 个农历年
  整数 + 24×201 个节气日，每 5 位存一天）。生成脚本 `tools/build_lunar_tables.py`
  用 `lunardate` 和 `LunarCalendar`（PyEphem）当基准逐日产出，开发时把 1900-01-31 –
  2100-02-08 的 **73058 天全对比过：农历 0 处不一致、节气 0 处不一致**（农历用
  `lunardate.YEAR_INFOS`、节气按太阳黄经）。表外面（1899-12-31 之前、2100-02-09
  之后）不是抛异常，而是回空串 —— 页面上顶多少一行小字。
- **法定节假日写在 `app/lunar.py::_HOLIDAY_PLAN` 里，一年一段**，出处是中国政府网的
  通知原文（现在有 2024 国办发明电〔2023〕7号、2025 国办发明电〔2024〕12号、2026 国办
  发明电〔2025〕7号）。**这是一年一发的公示数据，不要改成猜**：来年通知出来了，照格式
  加一段 `("春节", ("2-15", "2-23"), ("2-14", "2-28"))` 这样的元组就行，`_HOLIDAYS`
  在 import 时自动摊平成 `date → (名字, "休"/"班")`。调休上班的日子**名字留空、只显示
  「班」**（写「春节」会被读成放假）。
- 2027 年的安排还没发布，所以 `holiday()` 对 2027 回空 —— 不知道就说不知道。

### 开抢前的主动提醒

快开抢的时候机器人**主动**发一条微信过来，不用等你去问。用户 2026-10-09：

> 能不能让机器人在活动开始前"*分钟"主动通过微信发送最近时刻要抢的活动，走脚本不走ai模型
> ……改，但是要再设置里面增加这个功能的开关，增加这个提醒的时间自定义，限制单位为分钟，
> 最短时间5分钟。如果没有开启提醒功能则停止这个长轮询等额外的资源进程，只有打开提醒功能
> 才会启用各种辅助进程轮询，该功能默认"开"

实现全在 `app/reminder.py`（一个线程，**一次模型调用都不发**）：

- **几点该响**：`pipeline.next_openings()` —— 和 `/即将` 是**同一个函数**。重复活动
  （每天 / 每周 / 每月）的下一场由 `repeat.occurrence_on` 逐天展开，提醒不另算一套。
  自己另算的话就会出现「机器人说 09:00、提醒却在 08:50 响」，而重复活动恰恰最容易算错。
- **推给谁**：`ClawBot.state["context_tokens"]` 的键 —— 就是跟机器人说过话的那些人
  （每收到一条私聊就记下发言人和他的 `context_token`）。配了 `allowed_users` 白名单就取
  交集。还没人说过话就没人可推，静默跳过。
- **发得出去吗**：`ClawBot.send_text()` 只要一个 `to_user_id`，token 从状态文件里兜底，
  **不需要「正在回复某条消息」这个上下文**。它单独用一条连接池
  （`ClawBot.push_session()`）：`requests.Session` 官方没承诺线程安全，而提醒线程会在长
  轮询正抱着 `self.session` 等 `/ilink/bot/getupdates` 的时候插进来发一条 `sendmessage`。
- **为什么必须另起线程**：`poll_once()` 那次长轮询服务端最长挂 `longpolling_timeout_ms`
  （夹在 5~120 秒），一次最多阻塞 130 秒。检查要是塞在轮询循环里，最多能晚两分钟才发出去
  —— 提前 5 分钟的提醒只剩 3 分钟，等于白提醒。线程每轮最多睡 60 秒（`SLEEP_MAX`），
  宁可早看一眼，也不因为「刚睡下」漏掉一条一分钟前才录进来的活动。
- **一场只提醒一次**：台账直接用 `inbound_msg` 表（`db.seen_msg` / `db.mark_msg`，那张表
  就是干「这件事做过没有」的）。**去重键带场次时刻**，否则「每天 08:30」第二天就不会再响。
  **发成功了才记账** —— 先记后发的话，发送失败的那次就永远不会重试。
- **一条消息只说「最近的那一个时刻」**（`reminder.soonest()`）。用户 2026-10-09 的原话：
  「比如8点20分只提醒8点半的，8点半的内容合并在一起发送是合理的，但是下一个时刻9点和
  往后的活动，都不要带出来」。所以**同一时刻的几场合并成一条**（10:00 同时开四个活动很
  常见，一条列四行），**更晚的时刻一律不带**（混在一起会让人以为 9 点也马上要开抢，
  反而不知道该先盯哪个）。
  - 实现顺序不能反：`_send` 里**先按台账滤掉提醒过的，再取最近**。先取最近再滤的话，
    08:30 那批发完之后，08:33 得一直等到 08:30 开抢过去才轮得上，等于白丢了它自己的提前量
    （`test_a_later_moment_is_not_held_up_by_an_already_sent_one` 盯着这一条）。
  - 窗口一大这条规矩才看得出来：提前量 10 分钟时 09:00 本来就在窗口外，怎么都不会混进来；
    但用户把提前量调大（或用测试窗口）时，不加 `soonest()` 就会一次性把好几个时刻倒出来。
  - 每场仍然各自拿到自己的提前量 —— 一批发完，下一批**进入窗口**时再响，不是等着上一批
    开抢。
- **配额领满就不催**：`repeat.quota_state` 说本期已领满（日历卡片上那句「（本期已领满）」、
  机器人回执里那个尾巴，都是同一个函数），这条就不再提醒了 —— 让人白跑一趟比不提醒更糟。
  没领满的话，提醒里也会带上「（本周 0/2）」这个尾巴，口径和 `/即将` 完全一致。
- **过期/已完成的不提醒**：`db.list_range` 默认把 expired 也算出来（日历要它们灰着显示），
  但提醒只看 `status == "pending"`。

**设置页上的两个控件**：「活动开抢前主动发微信提醒」（默认**开**）和「提前多少分钟」
（默认 10，**最少 5**）。两点值得留意：

- **关掉 = 线程根本不存在**，不是「开着线程什么都不干」：`Reminder.sync()` 按设置决定建不建，
  关着的时候提醒线程、它那个连接池、它每分钟一次的查询一样都没有。用户那句「停止这个长轮询
  等额外的资源进程」指的是**提醒功能自己的**那些进程；微信那条**收消息**的长轮询不能关
  （关了机器人连回话都不会了），它一直开着。
- **保存就当场生效**：`web._sync_reminder()` 在 `POST /api/settings` 之后直接调 `sync()`，
  所以页面上关掉是当场把线程收掉，不用等容器重启。
- 「提前多少分钟」填小于 5 的数是**拒绝**（400 + 一句说明），不是悄悄夹成 5 —— 用户填 1、
  页面回 5，那是偷偷改人的数。读的时候另有一层夹紧（`settings.remind_minutes()`）：旧版本
  写的行、手改过的库、写到一半断电，都可能留下一个 1，而 1 分钟的提醒等于没有。
- **提醒末尾也带那句「一言」**（用户 2026-10-09 要的），用的是机器人自己那个
  `sayings.Sayings`（同一个池子、同一条连接、**同一个开关**）—— 设置里那个「一言」关掉，
  提醒也一句都不带、连那个接口都不去请求。取不到就是「这条不带」，提醒照发。

### 配 API key

**最省事的办法是在网页上配**：打开日历页面 → 右上角 **设置** → 填 base_url /
key / 模型 → 「测试」→ 保存。**存完立刻生效，不用重启容器**，也不用碰 NAS 的
命令行。设置存在库里（`settings` 表），优先级是：

```
网页上存的  >  环境变量  >  config.json
```

所以网页上配过的会盖住 `.env` 和 `config.json`；在网页上清空某一项，就回落到底
下那一层。key 永远不会明文回传给浏览器，页面只显示 `sk-1…cdef` 这样的掩码，把
掩码原样提交回来不会覆盖已存的 key。

`python main.py check` 的自检也认这一层：它看的是 `LLM.configured`（每次调用现读
「库里的设置 > config.json」），所以「key 只在网页上填过」的实例会写
「✅ 模型连通（key 来自页面里填的）」。早先它只看 `config.json`／环境变量，于是
**在网页上配好的实例跑自检会误报「没有 api_key」并退 1** —— 用户 2026-10-07 拿着这句
假故障去排障，越查越懵（见下面「踩过的坑」）。

不想用网页也行，`config.json` 里 `providers.<name>.api_key`，或者设环境变量：

```bash
WOOLBOT_API_KEY=sk-xxx          # 环境变量写法
```

想换模型就改 `provider` + `providers` 段，任何 OpenAI 兼容的
`/v1/chat/completions` 都能用：

```json
{
  "provider": "ollama",
  "providers": {
    "ollama": {
      "base_url": "http://192.0.2.100:11434/v1",
      "api_key": "ollama",
      "model": "qwen2.5:14b",
      "vision_model": "qwen2.5vl:7b"
    }
  }
}
```

`vision_model` 是截图识别用的模型；留空就退回 `model`。**2026-10-10 起页面上的两个框
合并成了一个**（用户：「把设置里面模型框的『文字模型』和『图片模型』合并成一个」）：
`web/index.html` 里只剩一个 `#sModel`，`web/app.js` 发设置时 `model` 与 `vision_model`
写同一个值，`test_the_merged_model_box_feeds_both_keys` 盯着这条链子。库里仍然是两列、
config.json 里也仍然可以分开写（缺 `vision_model` 就按 `model` 走）—— 合并的只是页面，
不是数据模型。

`wechat.save_media` 控制「收到的截图要不要在磁盘上留一份」（默认 `true`，存到
`wechat.media_dir`，容器里就是 `/app/data/media`）。**改成 `false` 就一张都不留** ——
图照样会被解密、送给模型识别，只是不落盘；这个值不写进 `.env`，改完
`docker compose restart woolbot` 生效（不用重新 build），已经躺在 `data/media/` 里的
旧文件不会自己消失，要自己删。落盘发生在识别**之前**，所以识别失败时文件也在。

它会：上传代码 → 生成/复用 `config.json`（web token 会沿用，否则手机书签失效）
→ `docker compose build` → `up -d` → 打印带 token 的日历地址。

API key 推荐直接在网页上配（见上一节）。要写进 `.env` 也行：

```bash
# NAS 上，woolbot 目录里
echo 'WOOLBOT_API_KEY=sk-xxx' >> .env
docker compose up -d
```

之后打开日历页面（2026-10-11 起，扫码这块在**设置 → 功能**页最上面，不在页面上了），
那里会出现「⚠️ 微信未登录」和二维码，微信扫码即可。
二维码约 5 分钟失效，页面每 5 秒查一次状态，过期会自动换新的；等不及就点
「刷新二维码」，它会真的去上游申请一张新的（不是把旧图重下一遍）。
这个按钮**在主循环退避的时候也管用**：`ret=-14`（token 失效）之后官方会暂停这个
账号一小时，机器人正是睡在这一小时里等；刷新请求会把它提前捅醒，立刻去申请新码
（见下面「踩过的坑」）。

旁边那颗「退出微信」只丢掉 **NAS 上存的这份登录**（`data/weixin_state.json` 里的
token 和游标），**撤销不了微信那边的授权** —— 协议里没有「解绑」这个动作，能做的
只有跟服务端说一声 `notifystop`。它的用处是：你在手机微信里「解除连接」之后再点它，
不用干等那一小时冷却，几秒就会出现新二维码。（真要在微信里彻底解绑，还是得去
微信里点「解除连接」；两边是两本账。）

没配上 API key 也能部署：日历页面和扫码登录都不需要模型，只有「读懂消息」才需要。
这时候机器人会在微信里回一句「还没配 API key」，页面顶部也会挂一条横幅，
点「去配置」就能填 —— 填完存下就生效，**不用重建容器**。

页面默认要求网址带 `?token=`。扫码登录之后手机浏览器会记住这个 token；
要是你想让局域网里任何设备直接打开，可以在设置里关掉「需要口令」，
之后不带 token 也能进（代价是同一局域网里的人都能看、都能改）。

### 端口：容器里监听 16886

容器里监听的端口是 **16886**（`app/config.py::DEFAULT_WEB_PORT`，全项目只有这一个
默认值），对外的映射也是同一个号（`docker-compose.yml` 里 `- "16886:16886"`）。
2026-10-10 从 8080 改过来的 —— NAS 上 8080 被别的东西惦记上了。

改端口要同时动**四个地方**，漏一个就是「页面打不开」或者「容器一直 unhealthy」：

| 地方 | 写的是什么 |
| --- | --- |
| `app/config.py::DEFAULT_WEB_PORT` | 唯一的默认值，`resolve_port()` / `front_url()` / `main.py` 的兜底都引用它 |
| `docker-compose.yml` 的映射 | 两侧同号（左边宿主机、右边容器内） |
| `Dockerfile` 的 `EXPOSE` | 只是文档作用，但别留个旧数字 |
| `config.example.json` 的 `port` / `public_port` | 手抄一份配置时的样板 |

`tests/test_main.py::DeploymentPortTest` 会替你盯住这四处是不是同号。`Dockerfile`
的健康检查是**现读** `config.json` 里的端口的（读不到才用兜底值），因为写死一个数字
的下场很坏：改了端口而漏改那一行，容器会一直 `unhealthy`，而页面其实是好的。

NAS 上还有一层反代指着这个端口：2026-10-10 实测外网域名
`https://calendar.example.com:5668` 是 **Lucky** 转进来的（进程
`/vol1/@appcenter/Lucky/bin/lucky`，面板在 `http://<NAS>:16601`，规则存在
`/vol1/@appdata/Lucky/data/lucky_reverseproxy.lkcf`，root 权限、普通用户读不到）。
**改容器端口必须同时去 Lucky 把那条规则的目标端口改成新的**，否则外网地址会变成
`502 Bad Gateway`；局域网的 `http://<NAS>:16886` 不受影响。那天测的时候外网地址
**本来就是 502**（当时 8080 上的服务是好的，所以规则的目标多半压根不是它 —— 具体
得在 Lucky 面板里看），改端口这件事没有把它变得更坏，但也没能顺手验证它。

### 口令、外网域名与访问秘钥

这三样都在**设置**弹窗里（2026-10-10 起它们同属弹窗里那一段「安全」，同段还有退出登录），
改完存下**立刻生效**（口令不用重启容器）：

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| 需要口令 | **开** | 关掉之后同局域网任何设备直接打开 |
| 页面口令 | 空（用 `config.json` 里那个） | 自定义，至少 4 个字符。填了它，**旧口令当场失效**，手机上的旧书签要重新存一次 |
| 用外网域名访问 | **关** | 打开后要填域名，如 `wool.example.com`（不带协议也行，会自动补 `https://`；带 `http://` 就保持 http） |
| 打开页面要访问秘钥 | **关** | 打开后只要填**一把秘钥**（2026-10-09 起没有用户名了）。至少 8 位，**大写字母、小写字母、数字、符号都要有** |

**口令和秘钥是叠着的两层：先口令，后秘钥。** 两个开关各自独立：可以只要口令、只要秘钥、
或两个都要。**没带口令的人看到的那张登录页是假的** —— 外观和真登录页一模一样，但上面
填什么都进不去（2026-10-09 定的，见下面那条）。

- **为什么要自定义口令**：`config.json` 里那个 token 是部署时 `secrets.token_urlsafe(12)`
  生成的乱码，只能靠 SSH 上去看。现在能在页面上改成自己记得住的。
- **为什么要有域名开关**：机器人回 `/日历` 时要说一个**能点开**的地址。容器里看到的是
  docker 网桥地址（`172.x`），根本不是你能访问的；所以部署时 `deploy/deploy_woolbot.py` 会把
  NAS 的真实地址和端口写进 `config.json` 的 `web.public_host` / `web.public_port`。
  挂了域名（反代、DDNS、内网穿透）就把域名开关打开，地址优先用域名。
- **秘钥是怎么回事**：会话值就是 `sha256(盐|秘钥|版本号)` 的前 32 位，塞在 cookie 里。
  **没有会话表** —— 改秘钥等于所有旧 cookie 一起失效，不用去清谁。有效期 **7 天**。
  版本号（`settings.login_epoch()`）是「退出登录」用的：点退出时把它 +1，**所有设备
  一起退**。只发一条 `Max-Age=0` 是不够的 —— 会话值不含时间也不含随机数，光清浏览器
  的话，抄走过 cookie 值的人照样能一直用（真机上验过：退出之后拿旧 cookie 打
  `/api/calendar` 还是 200）。`/api/health` 免鉴权，别把它挪到秘钥门后面
  （容器健康检查要打它）。
- **秘钥的格式是「不合规就拒绝」，不是「悄悄帮你改」**：长度不够就报「秘钥至少要 8 位」，
  缺哪一类就报「秘钥还要有数字」（一次把缺的都列出来）。存进去的是你**原样**填的那串，
  空格也算符号 —— 免得「填的是这个、存的是那个」这类没法排查的问题。
- **口令页伪装成秘钥页（2026-10-09，用户原话「设置访问口令以后，这个页面要伪装成
  秘钥进入」）**：`web.token` 挡人的时候，回的**就是**那张秘钥登录页（两层共用一份
  `_LOGIN_HTML`），一个字的口令线索都没有。老版本那张页面把 `?token=…` 的模板、
  「口令在 config.json 的 web.token / settings 表的 web_token 里」全印在页面上 ——
  看不见的人不知道有这道门，看得见的人直接就知道去哪儿抄钥匙。
  **没带口令时那张是假的，什么都不认**（用户 2026-10-09 先让助手复述理解、确认过
  四条才动手）：框里填访问秘钥、哪怕填的就是那把**对的**秘钥，也一律「秘钥不对」，
  一步都别想进来 —— 否则口令这层等于白设。它的用处只有一个：让不知道口令的人在
  那儿试，试两次就被 24 小时错误保护关掉，每一次提交都**算一次失败**（不然那页面
  对猜的人没有任何代价）。
  **口令带对了之后看到的那张才是真登录页**，认得访问秘钥；只开秘钥、没开口令的机器
  上看到的也是这张。**两张页面外观一模一样**（同一份 `_LOGIN_HTML`，同样写着「请输入
  访问秘钥」、同一个输入框），只有「哪把钥匙能开」不同 —— 所以没带口令的人察觉不到
  上面还有一层口令。判断分两步，别写混：
  - `_token_door()` = 口令那层**算不算数**（设了口令 + 开关开着）；
  - `_token_ok()` = 这一次**带没带对**口令（`?token=` / `X-Token` / cookie 三选一）。
  `_api_login` 里 `fake = self._token_door() and not self._token_ok()` 就是「这张是假页面」。
  - **口令页绝不种口令 cookie**（`_login_page(plant_token=False)`）：在这一层把口令
    发出去，这道门就等于不存在；成功登录时才由 `_api_login` 一起补上，所以「在门口
    输一次秘钥」就能一路进到里面。
  - 只开了口令、没开秘钥的机器上，口令过了就**直接放进去**（那儿压根没有秘钥这道门，
    再要一次是死胡同）。
  - 知道口令的人被 303 送回 `/` 的时候，页面上会多一句「**请先登录**」—— 而不是
    沉默地把同一张表单再画一遍。真机上一定会碰上这一步：主人拿着 `?token=` 进来、
    秘钥还没过，浏览器转一圈又回到**长得一模一样**的页面，一句话都没有的话看着就像
    「口令填错了」，再乱试两次就吃 24 小时禁令。这句话和接口那条 401 是同一个说法，
    **不提口令也不提秘钥** —— 蒙在鼓里的人照样看不出上面还有一层。
- **秘钥错误保护（2026-10-09 加的）**：只要**还有门站着**（两层开关任意一层开着），
  **同一个 IP 或同一台设备**哪一边错满 2 次，就**整站禁止访问 24 小时** —— 页面变成
  一页「🚫 暂时不许访问」，接口回 403（`{"banned": true, "retry_after": 秒数}`，页面上
  会显示还剩几小时几分钟）。连**正确的**秘钥也不认，否则字典攻击照样能试；**连已经
  登录的浏览器也一起拦** —— 「禁止访问」不是「没登录的才禁止」，否则被禁了还能用跟
  没禁只差一个旧 cookie。
  上限是 **2** 而不是 5，正是被上面那条改动逼出来的：那张伪装页谁打开谁都看得见，
  5 次太宽裕了。
  设备号是第一次打开登录页时种下的一个随机 cookie（`woolbot_device`，一年有效），
  所以换 IP（手机切流量、宽带重播）也躲不掉。两条账分开记：只在**带了设备 cookie**
  时才记设备那条，不然所有「第一次就来 POST」的客户端会共用一个空号码，一个人错两次
  把别人一起关。**失败一律记账，不看秘钥登录开没开** —— 那张伪装页本来就是猜钥匙的
  地方。`/api/health` 不受禁令影响。
  **禁令跟着「还有没有门」走**：只关「打开页面要访问秘钥」是不够的（口令那层还站着，
  它同样是被猜的那张伪装页），**两层开关都关掉**才算把门拆了。**禁令只在内存里**
  （重启容器即解除）：这是有意的自救通道 —— 万一在外面把自己关在外面，重启一下容器
  就能进去，而这也和「限流不落库」的既有做法一致。

**地址只在一个地方算**：`settings.front_url()`。启动日志和 `/日历` 的回复全走它，
所以改了口令或域名，这两处会一起变（`/日历` 当初被删掉，就是因为它自己拼了
一个写死的 `http://<你的NAS地址>:8080/` —— 见下面「踩过的坑」）。

## 三、命令

| 命令 | 干什么 |
| --- | --- |
| `python main.py web` | 只起日历页面 |
| `python main.py chat` | 命令行对话（调试用，不碰微信） |
| `python main.py bot` | 只起微信通道 |
| `python main.py all` | 微信通道 + 日历页面（**NAS 上跑这个**） |
| `python main.py check` | 自检配置、数据库、模型连通性 |
| `python main.py backfill-repeat` | 给**旧数据**补判重复规则和「每周/每月几次」（见下），`--dry-run` 只看不改，`--all` 连已有规则的一起重判 |

**为什么需要 `backfill-repeat`**：重复规则和配额都是后加的功能，之前入库的活动那几列是空的。
它们没法靠「下次再说一遍」补上（用户不会为两条已经在库里的券重发一遍），但
`raw_text` / `note` 里往往就抄着原文（「每日 09:00:00 起发放」「领券时间：每天
08:30:00-22:00:00」「单用户单周限领1张」「领券时间为每自然月10号10:00-20号23:59:59」）。
这条命令把这两段原文拼起来送进同一个 `repeat.py`、**不调模型**，认得出就写进那几列
（截图录进来的活动，规则可能只留在 `raw_text` 那段 OCR 原文里 —— 2026-10-10 起
`raw_text` 也喂给解析器，理由见「六、踩过的坑」里工行月月刷那一条）。

它认的是**两类东西**，补的时候待遇不同：

- **排期**（`repeat_kind` / `repeat_at` / `repeat_days` / …）：只有**还没判过规则**的行
  才写。已经判过的多半是用户在日历上手工填的，重读原文很可能把它们改错 ——
  那要显式 `--all` 才动。
- **配额**（`quota_week` / `quota_month`）：**补，但不动已经有的**。原文里没写配额的
  行，不能被这次重读补成空。（2026-10-10 才把这条保证补全：以前只有「已经有排期的行」
  走合并，**还没有排期的行**是整组照写 `fields_from()` 的结果，于是模型自己填好的
  「月限1次」被一句认不出来的原文抹成了空 —— 见「六、踩过的坑」里工行月月刷那条。）

`--all` 是给「解析器修好之后」用的：第一次回填把用户那条每周五的券认成了每周三
（备注里「每人每周三**档**力度」排在「每周五中午12:00」前面），修好解析器之后得
能重判一遍，否则用户只能自己一条条改。`--all` **只写「这次认得出规则」的行**，
认不出的一律不动 —— 免得把用户在日历上手工填的规则清掉。

微信里可用的指令：`/今天` `/即将` `/统计` `/help`（`/help` 与直接发
「使用帮助」等价，都不走模型；同一段字在页面右上角的「使用帮助」按钮里也能看到，
弹窗大标题 2026-10-11 起是「woolbot使用帮助」）。
**这两条通道的分工，2026-10-09 起写进过帮助**（用户当天点名要「写明白怎么问是不调用 ai
直接走脚本回复，怎么问才会调 ai，专业的术语表达，不要用大白话去描述」），`HELP_TEXT` 末尾
因此多过一节【调用方式】；**2026-10-10 与 2026-10-11 他两次亲手把整段帮助换成自己写的那份，


填分类字母／关掉开关就一句都不取）。**2026-10-11 那版连 `d,i,k,h` 都不在帮助里出现**
（「留空：默认文学、诗词、哲学、影视」+「填分类：根据页面提示输入对应字母」）。
**11 个字母的清单不在帮助里重写一份**：
权威是 `app/sayings.py::CATEGORIES`，服务端把它当 `sayings_categories` 交给
`/api/settings`，页面写进设置弹窗里那个框下面的 `#sSayingsCats`
（`test_the_sayings_categories_are_spelled_out_where_they_are_typed` 逐个字母核对，
`test_the_page_has_the_switch_wired_up` 盯住那个 span 被脚本真填上）。

`/日历` **2026-10-07 取消过，2026-10-09 又放回来了**（用户要求「同步增加『/日历』
指令，机器人脚本规则回复前端地址（随域名和自定义口令自动变化）」）。它 2026-10-07
被删的原因不是「不该有这个指令」，而是它当时**自己拼**了一个写死的
`http://<你的NAS地址>:8080/` —— 看着像真地址，谁也点不开。现在它回
`settings.front_url()` 算出来的真地址（域名、端口、口令都跟着设置走），
和启动日志里那行「日历页面已启动」是同一个来源。这条路仍然**不走模型**。

想删掉一条已经记过的活动，直接说关键词就行：**「删除梦享」「把临沂那个删了」** ——
机器人会把匹配到的列出来，你回编号（「1」「1 2」「第一条」）它才删；回「都删」全删，
回「取消」一条都不动。删除这一步也能问模型（`intent="delete"` + 关键词），
但**模型没有删除能力**，详见下面「工作方式」第 6 条。

## 四、工作方式（为什么它不会瞎报）

三层各管一件事，**模型不接触数据库**：

```
你的话 ──LLM──▶ 结构化条件 ──SQL──▶ 命中的行 ──Python──▶ 排版好的回复
        （只翻译）        （只检索）        （只排版）
```

- **模型只做「自然语言 ⇄ 结构化」的翻译**：录入时抽取字段，查询时翻译成
  `date` / `time` / `keyword` 这类条件。它看不到库里有什么，所以不可能编出一条
  不存在的活动。
- **检索交给 SQL**：查询结果由 `grab_in_window()` 这类查询直接给出。
- **排版交给 Python**：时间、平台、有效期的拼接是确定性的代码，不是模型复述。

时间上的四条防线：

1. **注入当前时间**：每次调用都告诉模型「现在是 2026-10-06T19:22 周二」，
   否则它算「下周三」会飘。见 `app/timeutil.py` 的 `anchor_block()`。
2. **反问而不是瞎猜**：没听清时间就存成「时间未定」并反问；算出来的时间落在
   今天之前（多半是把「下周三」当成「本周三」）会拦下来问清楚。但如果只是
   「今天早些时候」——你很可能就是在补记一条已经开抢的——它会照记，而且
   **回执里一个字都不多提**（2026-10-10 用户把原来那句「⏰ 提醒一句：… 的开抢时间
   已经过了」划掉了：「就算时间已经过了也没关系，不用提醒，就正常录入就行了」）。
3. **查询侧的日期兜底（`app/pipeline.py` 的 `_fallback_day`）**：模型算日期会算错，
   而算错是**静默**的 —— 你问「周三抢什么」，它若没给出日期，老代码会默默退回
   「今天」，你拿到一份今天清单、还以为那是周三的。这种错最伤人。所以：

   - 模型**一个日期都没给** → Python 从原话里确定性解析一次
     （今天/明天/后天/大后天/昨天/前天、周三/星期三/礼拜天、上周三/下周三/本周三），
     解不出才落到今天；
   - 模型给的日期和原话里**无歧义**的日子词对不上，且它只给了一天 → 以原话为准
     （「从明天到这周五」这种区间不碰）；
   - 周几不带前缀时按**最近的**那个算：周三下午问「周二抢什么」，指的是下一个周二。

   理由很直白：「今天」「周三」是纯确定性的东西，Python 解比模型可靠，而且错了能被
   测出来 —— `tests/test_core.py::FallbackDayTest` 把它锁住了。
4. **录入侧的两道修正（`_align_day` / `_repair_end`）**：同一种错在录入侧更隐蔽。

   - *日子拨正*：你说「明天上午9点半京东」，模型记成**今天** 09:30。只要现在还没到
     09:30，上面第 2 条的检查就拦不住（它只拦「落在今天之前」），活动会静默躺到错
     日子上，到点也不提醒。所以 `_align_day` 会用和查询侧同一套词表复核一遍，以原话
     为准把日子拨正（开抢时刻的**钟点不变**，与它同一天的 start/end 一起搬）。
     两道护栏，免得它帮倒忙：原话里必须**只有一个**日子（「明天开抢，有效期到后天」
     有两个，猜不出哪个词管哪个字段，交回给模型）；模型给的日期若**早于今天**一律不碰
     —— 那是「补记一条已经开抢的」，该走第 2 条去问你，不该被悄悄挪到下周。
   - *有效期推顺*：有效期是拿 `end_at` 判过期的（`db.refresh_expired()`），所以一个
     算错的 `end_at`（开抢 10-07 09:00、有效期却写 10-06 23:59）会让刚记下的活动在
     日历上**直接灰掉**，你还以为白记了。`_repair_end` 按天把它推到开抢当天。
     还有一种日子看着没错、**时刻**却倒挂的：你说「到晚上12点」，口语里那是当天 24:00
     （即第二天 00:00），模型很容易写成当天 00:00 —— 按天补是补不动的（天数为 0），
     得再往后推一天。

   `tests/test_core.py::IngestDateTest` 锁住这两条。
5. **固定句式的查询根本不叫模型（`app/pipeline.py` 的 `parse_fixed_query`）**：用户
   2026-10-07 定下的规矩 —— 查询用固定句式说，「本周六抢什么」「明天8:30抢什么」
   「本周五8:30抢什么」。这些句子里只有三样东西：日子、时刻、查询词，**全是确定性
   的**，Python 解出来直接查库，省掉一次模型往返（微信里几乎秒回），也顺带消掉了
   「模型把周六算成周五」这类错。两条纪律：

   - **只有整句话正好是「日子 + 时刻 + 查询词」时才走快路**。做法是把认得的词全摘掉，
     还剩一个字就交回模型 —— 否则「明天9点京东超市满99减50抢券」会被当成查询，
     用户看到「那天没有活动」而不是「已记下」。
   - **快路和模型路必须给出同一种答案**，所以快路返回的形状就是模型给的那份 JSON
     （`{"intent": "query", "date": ..., "time": ...}`），下游 `_apply_query` 一个字
     都不用改。只说时刻不说日子（「9点半抢什么」）时按今天算 —— 和模型路的缺省一致。

   **微信里只回摘要**：查询回复只有「时刻 + 标题」（`_row_line` / `_render_hits`），
   平台、有效期、备注、链接一律不回 —— 那些能占半屏，想看就去日历页面。**录入回执
   不在此列**（用户明确要保留 📝 备注，那是他刚投喂的内容，得能当场核对）。
   `tests/test_core.py::FixedQueryTest` 把两边都锁住了。

   **录入回执的末尾还附一条日历地址**（用户 2026-10-10 的原话：「每次通过 clawbot
   录入活动以后（只有这个情况下），回复内容里应该附带日历地址，这样每次录完都能
   方便去前端检查」）：就在「问一句「今天抢什么」就能查。」下面空一行，形如
   `📅 日历页面：<地址>`，地址仍旧只由 `settings.front_url()` 算（和 `/日历` 指令、
   启动日志是同一个实现）。**只有真记进去东西的那条回执带它**：「ℹ️ 没读到新的活动
   内容」和「ℹ️ 这条已经记过了」两条都不带 —— 那两回没录进东西，而用户要的是
   「录完去核对」。查询、统计、帮助这些回复一律不带。
   `tests/test_core.py::test_the_ingest_receipt_hands_back_the_calendar_address`
   两头都钉住了。

   两条 2026-10-07 补上的配套：

   - **中文数字也认**（用户点名「今天十五点抢什么」）：`_cn_int` 把「十五」「二十」
     「九点二十」翻成整数，于是 `15:00`、「15点」、「十五点」、「下午3点」四种写法
     落到同一个 `time`。时刻正则**必须带 `:` 或「点」**才认，不然「10月9号」里的数字
     会被当成时刻（这个坑真踩过）。中文数字表只定义**一份**（`_CN_DIGITS`）：
     删活动那条路靠它认「回第二条」的「二」，两处各写一份的话先定义的那份就没人用了。
   - **「使用帮助」直通**（同一个 `cmd` 判断，不调模型）：微信里发「使用帮助」
     「使用说明」「怎么用」「/help」都直接回帮助文本；页面右上角的「使用帮助」按钮
     走 `GET /api/help`，返回的是**同一段** `HELP_TEXT` —— 两边各写一份迟早会说法不一致。

6. **重复活动（`app/repeat.py`）**：手机银行那种券的备注里写着「每日 09:00:00 起
   发放」「领券时间：每天 08:30:00-22:00:00」「每周五中午 12:00 开始发放」，本质是
   **每天/每周都发生**，不是一次性事件 —— 而早先的表只能记一次性，于是「后天抢什么」
   怎么答都不对（用户就是这么发现它的）。后来用户又补了一句：备注里还有
   **「单用户单周限领1张」「单用户单月限领1张」** —— 一周能领几次、一月能领几次，
   是这条活动的一半信息。所以现在表里是两**组**列：

   | 组 | 列 | 意思 |
   | --- | --- | --- |
   | 排期 | `repeat_kind` | `daily` / `weekly` / `monthly`（NULL = 一次性） |
   | | `repeat_at` / `repeat_until` | 每个周期里开抢那一刻 / 当天可领到几点 |
   | | `repeat_weekday` | 0~6（周一=0），老列，只有单个星期几的 weekly 用 |
   | | `repeat_days` | weekly 的**多个**星期几，如 `"1,3"` = 每周二、四 |
   | | `repeat_month_days` | monthly 的日号，如 `"1,15"` = 每月1日、15日 |
   | 配额 | `quota_week` / `quota_month` | 每个自然周 / 自然月最多领几次 |

   分工和上面两条同一个哲学：**模型只负责认出「这条是重复的」**（提示词里多一个
   `repeat` 字段，写成「每天 09:00」「每天 08:30-22:00」「每周二、四 10:00」
   「每月1日、15日 10:00」「每自然月10号 10:00」这样的人话），至于它到底落在哪几天、
   哪一刻、配额是多少，一律由 `app/repeat.py` 算。

   模型忘了说还有三路兜底，`fields_from()` 按顺序找：**模型的 `repeat` 字段 → 它写的
   `note` → 用户原话 → 截图 OCR 原文（`raw_text`）**。最后那一路是 2026-10-10 补的：
   截图那条路没有「用户原话」，而模型有时只在 OCR 原文里留下「领券时间为每自然月10号
   10:00-20号23:59:59」，那条工行月月刷券（`activity#74`）就这么静默退化成了一次性
   活动。**配额故意不吃 OCR 这一路** —— 排期认错看得见，配额认错是静默少领。

   「每**自然**月10号」这种写法也认（`_MONTHLY_RE` 里那个 `(?:自然)?`）；同理紧跟在
   号数后面的「结束/截止/为止」说明它讲的是周期**结束**不是开抢日（「每自然月30号结束
   每期消费达标活动」），那一条要跳过。**规则里的时刻只认排期词旁边那个**：截图 OCR 的
   第一行常是手机状态栏的钟点（`09:34 5G 70%`），以前按「全文第一处」找就会把规则锚到
   09:34 上（`_time_near` 现在先看排期词后面 24 个字，找不到才退回全文）。

   「每周三次」里的**数字是量词不是星期几**，「每周三**档**力度」里的「档」是力度
   档位不是次数 —— 两条判据都写死在解析器里（`_MEASURE_CH`、必须带「日/号」）。
   真数据里的「每人每周三档力度乐园门票消费券」曾经把「每周五中午12:00」认成周三。

   **配额和排期在接口上是两组字段**（`repeat` 一句话 + `quota_week`/`quota_month`
   两个数），Web 编辑框也分成三格。理由：`repeat` 那句话是**要重新解析的**，把
   「· 周限1次」混进同一句话里，用户再存一次就会被解析器改写。所以列表接口另外给
   一个 `repeat_input`（纯排期那句）专门喂编辑框。

   **按天记账（`activity_done` 表）**：重复活动没有「整条完成」这回事 —— 一格
   `status` 装不下几十场，今天点了完成明天整条都成了完成，用户就再也看不到「这周
   还剩几次」。所以「这一天领到了」记在 `activity_done(activity_id, day)` 里，
   行级 `status` 对重复活动只有 `expired` 一个意思（`repeat.occurrence_status` 明说了
   这件事）。页面上重复活动的按钮因此是「标记**本次**完成 / 撤销本次」。

   **配额感知**（用户 2026-10-09 定的规矩）：一周/一月的额度用满之后，那一期里剩下
   的场次**都显示已完成**，下期自动恢复待抢 —— 再显示「待抢」是在骗人，点进去也
   领不到。机器人侧同一个数：清单里每条重复活动带「（本周 1/2）」「（本期已领满）」，
   和日历上那张卡同源（都调 `repeat.quota_state`）。

   两处配套的关键实现：

   - `db.list_range()` 会把「区间内有场次」的重复行**并进结果**（`_repeat_rows_between`
     只做粗筛，精确判断仍调 `repeat.py`）。因为重复行只有一个 `grab_at`，光按它查，
     问「后天」会答「没有活动记录」—— 用户报的就是这个。
   - 前端**不自己算规则**：接口直接给出行内 `occurrences`（每一场带自己的
     `status` / `done` / `quota`），日历只负责摆到格子里。两套算法分叉过一次，结果
     就是日历和机器人各说各话。
   - 同理，「这一天**还能领、但不是这天开抢**」也由后端按机器人那对判据算好
     （`/api/activities` 每行带 `claimable_days`，判据就是 `pipeline.opens_on` /
     `claimable_on` 本体，不是复制品）。少了它，日历点开某天会说「这天没有活动」，
     而机器人同一天说「📌 不过这一天还能领的」—— 又是两边对不上。
   - 那些活动**必须把开抢的日子写出来**：右栏标题清单里它们只写标题（本来就不带时刻），
     点进详情后「开抢」那行写的是 `10月3日 10:00` 而不是 `10:00` —— 从「还能领的」
     跨天点进来的，光写时刻会被读成「今天 10:00」。

   老库靠 `db._migrate()` 原地 `ALTER TABLE` 补列（`CREATE TABLE IF NOT EXISTS` 对已存在
   的表什么都不做，而用户库里已经真有数据，**不能重建表**）。新加的四列同样走它，
   `activity_done` 则是 `CREATE TABLE IF NOT EXISTS` 出来的新表。`repeat_weekday` 这个
   老列**留着没删**：老库里的 weekly 行只填了它，`rule_of` 认不出 `repeat_days` 时
   回退到它，所以老数据一行都不用迁。

7. **自然语言删除（`_handle_delete` / `_resolve_delete`）**：「梦享券提前结束了，删掉吧」
   这种话得有人干。同样是「模型只翻译、Python 做决定」：

   - 模型只需抽出**一个能定位活动的关键词**（`intent="delete"` + `keyword`）。
     提示词里写死了**它没有删除能力** —— 一旦它以为自己在删，就会开始输出活动列表，
     那等于让模型对着库瞎指。
   - `db.search(keyword)` 把匹配到的（最多 10 条）连编号和 `<#id>` 列出来，
     把 `{ids, titles, keyword}` 存进 `pending`（`kind="delete"`），**这一步一条都不删**。
   - 用户回编号（「1」「1 2」「第一条」）、「都删」、「取消」才真正落刀。编号越界
     **不做任何猜测**，而是把 pending 存回去再问一遍 —— 猜错的代价是不可逆的。
   - 模型答 `other` / `query` 时还有一层**动词兜底**（`_fallback_keyword`）：「删除梦享」
     「把临沂那个删了」这两句无论模型怎么判都能走到删除流程。只抢这两类意图，
     `ingest` / `confirm` 不抢 —— 「明天9点京东抢券，把旧那条删了」的重点是**记下来**。
   - 没有 `user_id`（没地方存待确认）时，宁可什么都不做，也不猜「大概是要全删」。

都不需要 API key，也不出网 —— 假服务器都跑在 `127.0.0.1`（端口都由系统分配，

这八套验的都是**代码**（协议、边界、回归）。「真模型抽得准不准」它们管不了，

`test_llm.py` 是补得最晚、也最值的一个：`test_core.py` 用 `FakeLLM` 把整个模型层

围栏的废话能不能抠出 JSON」「截图解密出来的字节能不能一路落到 SQLite」全都没被
测过 —— 而 `UNDERSTAND_PROMPT` 就是在这种盲区里带着一个「每次调用必抛异常」的
bug 活到了部署之后。

`test_main.py` 补的是另一块同类盲区：`main.py` 是用户唯一会直接敲的那一层，
却曾经没有任何测试碰过它。它跑的是真入口（真配置文件、真 SQLite、假 OpenAI 端点），

标记完成 / 删除」这四个按钮走的那几条接口，此前一直是**手工用 urllib 打一遍**

`test_settings.py` 锁的是「页面上配模型」这条链路上最容易反咬人的几处：

协议测试会断言请求形状 —— 比如 `sendmessage` 必须带
`msg.from_user_id=""`、`client_id` 和顶层 `base_info`，缺了就是「HTTP 200 但微信
收不到」的静默失败，这是这套协议最容易踩的坑。

## 六、踩过的坑（改代码前先看一眼）

**微信协议**

- `qrcode_img_content` 是 HTTPS **链接**，不是 base64 图片。而且那个链接指向一个
  **JS 渲染的网页**，直接下载只会拿到一坨 HTML —— 所以必须拿这个链接当载荷
  **自己生成二维码**（`app/qr.py`，用纯 Python 的 `segno`）。上游文档写的
  「优先下载二维码图片」实测走不通，它自己的兜底也是本地生成。
- 业务请求头里的 `X-WECHAT-UIN` **每次 POST 都要重新随机生成**。
- `sendmessage` 缺 `from_user_id` / `client_id` / `base_info` 会静默失败；
  正常节奏是 `getconfig` → `sendtyping(1)` → `sendmessage` → `sendtyping(2)`。
- 发出去的是**纯文本**（`item_list[*].text_item.text`），markdown 在这儿不生效 ——
  `**08:30**` 会在手机上原样显示两个星号。想让时刻看着更重，只能换字形：数学粗体
  数字 U+1D7CE..U+1D7D7（`pipeline.bold_time()` 就是这么干的）。它们是 astral
  字符，`len()` 算一个字符、`split_text` 按字符切安全，`requests` 发出去会编码成
  代理对（`\ud835\udfee`），标准 JSON 解析器能还原。
- `ret` / `errcode == -14` 表示 token 过期，官方会把该账号**暂停 1 小时**，
  不能无间隔重试 —— 代码里退避 3600 秒。
- **退避等待必须能被「刷新二维码」叫醒**。`_sleep()` 早先只是
  `self._stop.wait(seconds)`，于是 token 失效那一小时里，页面上点刷新只是把事件
  置了位、没人看：用户扫着那张已经作废的旧码、按了按钮、一点动静都没有
  （真机反馈「点过，没反应」）。现在 `_sleep()` 等的是 `self._wake` 条件变量，
  `request_qr_refresh()` 和 `stop()` 都会 `notify_all()`；被刷新叫醒时**返回
  False**（不是「该退出了」），主循环回到顶部、`logged_in` 已是假、`login()` 开头
  清掉标志并申请新码。两个配套细节：长轮询的退避用
  `_sleep(..., wake_on_refresh=False)`（人都登录着，二维码不需要，被叫醒只会让
  退避失效白打接口）；`logout()` 顺手把 `qr_file`/`qr_url` 清掉，免得页面继续
  摆着那张扫不动的旧码。
- 客户端自己超时（长轮询 35 秒没数据）是**正常控制流**，保留游标继续，不算失败。
- 带 `group_id` 的群消息直接跳过：协议没有群聊发送分支，私聊回复发言人等于发错人。
- 图片走 CDN + AES-128-ECB 解密；`aes_key` 有「base64 的 16 字节原始 key」和
  「base64 的 32 字符 hex」两种编码，都要兼容。

**部署（飞牛 NAS 上真踩到的）**

- `docker compose` 会自动创建缺失的 bind mount 源目录，但建出来是 **`root:root`**，
  容器里的非 root 用户写不进去，sqlite 报 `unable to open database file`。
  而且宿主的组 id 常常不是 1000（飞牛上是 `uid=1000 gid=1001`），镜像里写死的
  `1000:1000` 照样对不上。所以 `docker-compose.yml` 用
  `user: "${WOOLBOT_UID}:${WOOLBOT_GID}"`，真实的 uid/gid 由部署脚本写进 `.env`。
- `registry-mirrors` 的顺序很要命：**排在前面但不报错、只是慢的镜像站会硬卡死整个
  build**（实测 `docker.1ms.run` 卡在 `0B / 12.12MB` 整整 716 秒，docker 不会自动
  回退到下一个）。飞牛上 `docker.m.daocloud.io` 只要 11 秒，`docker.xuanyuan.me`
  已经改成要付费。绕开的办法是先 `docker pull docker.m.daocloud.io/library/python:3.12-slim`
  再 `docker tag … python:3.12-slim`，本地有了基础镜像，build 就不用碰镜像站。
- `web/` 是 **COPY 进镜像**的，不是挂载的。所以改前端之后必须
  `docker compose up -d --build`，用 `--no-build` 只会跑旧页面。

**HTTP 层**

- `create_server` 千万别写成 `int(web_cfg.get("port") or 8080)`：显式配的
  `port: 0`（意思是「让系统挑一个空闲端口」）会被当成假值吃掉，静默变成默认端口
  （当时是 8080，现在是 `config.DEFAULT_WEB_PORT`）。测试就是靠 `port: 0` 才能并行、
  互不抢端口的 —— 这个 bug 让所有接口测试实际上都去抢同一个固定端口，只有在那个
  端口恰好空着的时候才通过。现在解析逻辑单独放在 `resolve_port()` 里，可以直接断言
  （兜底值也改成引用 `DEFAULT_WEB_PORT`，不再多一个写死的数字）。
- 静态文件必须带 `charset=utf-8`，而**分支写重复就会漏**：`do_GET` 原本有一条
  「带 token 就顺手种 cookie」的独立分支，它自己调 `_send(...)` 却没补 charset。
  线上永远配了 token，所以线上永远走那条分支 —— `app.js` / `style.css` 一直是
  裸的 `text/javascript` / `text/css`。现在统一走 `_content_type()`，只有一条路径。
- `mimetypes` 对 `.js` 的判断在不同 Python/平台上不一致（`text/javascript` 还是
  `application/javascript`），别只比字符串，按 `text/` 前缀加明确名单一起判。

**设置页（在网页上配模型）**

- 设置表里空的 `api_key` 意思是「这项删掉，回落下一层」，而页面上空的 key 输入框
  意思是「我没动这个框」。**这两件事必须分开**：直接把表单发过来的空串塞进
  `settings.update()`，用户只改个模型名、key 框留空，已经配好的 key 就被静默清掉了。
  现在空串一律 pop 掉，真删要显式传 `clear_api_key`。
- 页面回显的是 `sk-1…cdef` 这样的掩码，**提交时要把掩码也 pop 掉**，否则下次保存
  会把掩码本身当成新 key 存进去。
- **不要在启动时给没配 key 的情况装一个「回答固定话术」的桩 LLM**。看着很稳，
  实际上让整个设置页失去意义：进程启动时就装配好了桩，用户在页面上填了 key
  也永远是那句提示，而进程一切正常、日志干干净净。正确做法是照常装配真 LLM，
  只在真正要发请求时检查 key 并抛 `NoKeyError`。
- `NoKeyError` 要单独成类并在 `_post()` 里**直接抛出、不进重试**：缺 key 重试
  三次只是让用户白等 7 秒，还会把一个「配置问题」伪装成「网络问题」。
- **`configured` 只说明「填了 key」，不说明「key 管用」**。打错一个字符，页面上的
  黄条就消失了，用户以为一切正常，只会在微信里收到一句报错 —— 这是本项目最坑的
  一种「看起来正常」。所以模型层的 HTTP 错误码会被翻成人话（`_explain_http`），
  其中「用户自己能修」的三类（401/403、404、400）会被记进 `settings` 表，
  页面据此把黄条换成红条。限流和 5xx **不记**：报了用户也只能等。
  模型调通一次就自动清掉，不用用户再去点一次什么。

**闲聊开关（设置页上的「允许机器人闲聊」，默认关）**

- 用户 2026-10-07 问「如果关闭闲聊功能，会不会影响现在的活动录入和活动删除功能」，
  最后选的做法是「**非活动消息一律固定话术**」+ 页面上一个开关（默认关）。
- 关掉之后：整句寒暄（`_SMALL_TALK`：你好 / 在吗 / 谢谢 / 你是谁 …，**整句相等**才算，
  所以「你好，明天9点京东抢券」照样是录入）在 `_handle_text_inner` 里就地回
  `CHAT_OFF_GREETING`，**一次模型都不调**；其余认不出是活动的消息回 `CHAT_OFF_HINT`。
  后面这条还是会为「判意图」问模型一次 —— 自由句子和活动录入在调模型之前长得一样，
  那一次省不掉，省掉的是原来那次 `llm.chat`。开着就是老行为：先用模型这次给的
  `reply`，没有再补一次 `llm.chat`。
- **它只碰闲聊**：`ingest` / `query` / `delete` 在那段代码的前面就 `return` 了；
  寒暄表也排在 pending（删除确认、录入反问）**之后**，否则一句「好的」会被当成寒暄
  吞掉。`LLM.chat` 本身**不能删**：设置页的「测试连接」（`app/web.py`）和
  `main.py check` 都用它（`chat("只回复两个字：可用")`），开关只做在流水线那个调用点上。
- 库里没设过 `chat_enabled` = 关（`settings.chat_enabled()`），清空该键也回落到关。

**一言开关（设置页上的「每条回复末尾带一句『一言』」，默认开）**

- 用户 2026-10-07 要求：「把一言的开关放进前端设置里面」—— 以前只能 SSH 上 NAS 设
  `WOOLBOT_NO_SAYINGS=1`，现在是设置弹窗里的一格，存了立刻生效。
- 两层：**环境变量更硬**（`WOOLBOT_NO_SAYINGS=1` 时页面开不回来），然后是库里的
  `sayings_enabled`（没设过 = 开）。判断只有一处：`app/sayings.py::enabled()`。
  那个开关**旁边还有一个「一言来源」框**（2026-10-09 加）：留空＝默认四类，写字母串＝挑
  分类，写 `http(s)://` 网址＝换一家，三种解释都在 `app/sayings.py::source_url()` 那一处
  （详见「一、它长什么样」里那两段）。**2026-10-10 起框下面还印着那 11 个可选字母**
  （`#sSayingsCats`，服务端给的 `sayings_categories`），不用再翻帮助去查 ——
  帮助里那句「可选字母」也随之删掉了。
- 关掉之后**一次请求都不发**：`tail()` 返回空串，`prefetch()` 也直接返回 —— 只挡
  `tail()` 是不够的，`app/wechat.py:251` 一启动就会调 `prefetch()`，那样等于
  「用户明明关了、容器还在偷请求 v1.hitokoto.cn」。用例：
  `tests/test_settings.py::test_the_page_switch_stops_the_sayings_fetches`。

**查询口径（按分钟问 vs 看全天）**

- **同一句「抢什么」，问法不同、该回的东西也不同**。按分钟问（「11:00抢什么」）问的是
  「第一分钟抢什么」，所以只回那一刻开抢的，再补一节**当天还没开始的**；已经开抢过去的、
  只能领不能抢的一律不带（用户 2026-10-07 的原话：「不要带出今天不能抢的活动」）。
  而「今天有什么活动」是看全天的清单，那条路**照旧**带「还能领的」一节。早先两条路
  共用同一节「还能领的」，于是问「9点半抢什么」会被一串长标题刷屏，用户真正要的那条
  还得自己找。
- **没有就到这里，不拿别的日子凑数**：早先按分钟问落空时会退一步给「🔎 供参照，接下来
  最近的」，把后面几天的活动抖出来；用户当天的原话是「我问今天的活动，为什么要把后面的
  给带出来，没有就结束就行了啊」，这一节（以及「没有活动记录」后面那节「接下来要抢的」）
  已经删掉，`query.show_nearest_hint` / `nearest_hint_count` 两个配置项一并取消。
  想看往后几天有专门的 `/即将`，那里的「最近」现在按**真实的下一次开抢**算（`_next_openings`：
  重复型逐天展开，见下条），所以「每天 08:30」的港城券不会再从「接下来要抢的」里消失。
  **这些取舍只写在这一节里**：用户 2026-10-07 看到我把它们写进机器人的使用帮助后说
  「这个不应该展示给我看吧」，所以 `HELP_TEXT` 只留「你能怎么问」和指令清单，
  不放行为说明（`test_the_help_text_only_teaches_what_to_send` 反向盯着这几个词）。
  （2026-10-09 有一次**定点反转**：「走不走模型」这一项被用户点名要求写进帮助；
  2026-10-10 与 2026-10-11 用户又两次亲手把整段帮助换成他自己写的那份，术语那一节随之消失、
  只剩末尾那句「标准句式或快捷指令 = 不调用AI」，见「三、命令」那节。这份黑名单本身一条都没动 ——
  新文案里仍然没有它们。）
  同一条规矩 2026-10-09 落到了设置页上：三个开关下面原本各挂一段「默认关：……」
  「关掉之后……」，弹窗顶上还有一句接口说明，用户把它们一起划掉，说「不应该展示出来」——
  所以设置弹窗里**只剩控件和必要的回显**（标题从「AI 模型设置」改成了「设置」，
  「留空则不改动已存的 key」这种不写就填不对的提示才留）。开关的默认值与后果写在这里，
  不写在页面上。
- **重复型的券要按天展开之后比时刻**：库里「每天 08:30」只有一行、日期停在最初录入的
  那天，SQL 拿 `grab_at` 跟窗口比是比不上这一天的 —— 「明天 8:30 抢什么」会答
  「没有开抢安排」，而「明天抢什么」明明白白列着 08:30（真机上就是这么自相矛盾的）。
  所以 `_rows_opening_at()` 先取 SQL 命中，再拿 `list_range(d, d)` 逐行问
  `_opens_at(r, d)`，把展开出来的那一刻补回来。`/即将` 用的是同一套展开逻辑
  （`_next_openings` → `repeat.occurrence_on` 逐天找下一场）。
- **中文数字要认**：「今天十五点抢什么」里的「十五」不翻成 15，整句话就会被当成
  「多写了别的字」丢回模型，白等一次往返、时刻还可能被模型算错。中文数字表
  （`_CN_DIGITS`）只定义**一份**：`_pick_indices` 认「回第二条」的「二」也用它，
  两处各写一份的话，先定义的那份就静默没人用了（这个坑真踩到）。

**开抢提醒（设置页上的「活动开抢前主动发微信提醒」，默认开）**

- **提醒不能自己算「下一场几点」**。`pipeline.next_openings()` 是唯一实现，和 `/即将`
  共用；重复活动的逐天展开只有 `repeat.occurrence_on` 一份。另算一套的结果是
  「机器人说 09:00、提醒 08:50 响」，而重复活动正是最容易算错的那一类。
- **去重键必须带场次时刻**，不能只带活动 id。「每天 08:30」今天提醒过、明天还得提醒；
  只按 id 去重的话，第二天起一辈子都不会再响。键是 `remind:{user}:{id}:{YYYY-MM-DDTHH:MM}`，
  台账直接用 `inbound_msg`（`db.seen_msg` / `db.mark_msg`，`INSERT OR IGNORE`）。
- **发成功了才记账**。先记后发的话，发送失败的那一次就永远不会重试 —— 而「发失败」
  恰恰是最需要重试的情况。同理，没登录时**不记账**：登录回来这一场要是还没开抢，
  还得提醒。
- **`db.list_range` 默认把 expired 也算进来**（日历要它们灰着显示），所以提醒必须自己
  再看一眼 `status == "pending"`，否则过期系列会被一遍遍催。
- **`requests.Session` 不能两个线程共用**。提醒线程会在长轮询正抱着 `self.session` 等
  `getupdates` 的时候插进来发 `sendmessage`，所以它单独用 `ClawBot.push_session()`
  （懒创建 —— 提醒关着的时候连这个池子都不该存在）。
- **主消息长轮询不能关**。用户说要「停止这个长轮询等额外的资源进程」，指的是提醒功能
  **自己的**那些；`/ilink/bot/getupdates` 一关，机器人连回话都不会了。所以「关提醒」的
  实现是**提醒线程根本不被创建**，不是开着空转。
- **提前量小于下限要拒，不要夹**。用户填 1、页面回显 5，那是偷偷改人的数 ——
  接口回 400 说明原因。读的时候（`settings.remind_minutes()`）另有一层夹紧，
  防的是旧版本写的行、手改过的库、写到一半断电留下的 1。
- **页面控件要在脚本里真的接上**。HTML 里摆了 `sRemind` 不够 —— 和 `settingsHint`
  那次是同一个教训：`fillSettingsForm` 不回填、`settingsPayload` 不发出去，页面上就是
  一个点了没反应的框。`test_the_reminder_controls_are_wired_to_the_page` 反向盯着这四行。
- **一条消息只说最近的那一个时刻，且「先滤台账、再取最近」**。用户 2026-10-09 划的规矩：
  8点20分只提醒 8点半的，同一时刻的几场合并，9 点及更晚的不带出来（原话见「二、跑起来」
  那一节）。顺序反了就会有隐蔽的副作用：先取最近再滤台账的话，08:30 发完之后 08:33 得等到
  08:30 开抢过去才轮得上，白丢提前量 —— 这种错不会报错，只会「有时候晚了几分钟」。
- **「一言」不许有第二个实现**（用户 2026-10-09 要「受设置里面的『一言』统一控制」）。
  提醒拿的是 `client.sayings`（`wechat.ClawBot` 里那一个），格式也直接用
  `Sayings.tail()`（`\n\n**句子**`）—— 自己 new 一个实例、或者自己拼一遍星号，
  就等于开关和排版各有两份，而「统一控制」要的正是只有一份。
- **「一言来源」那串字也只许有一处解释**（用户 2026-10-09 要「在设置里面增加一言的自定义源」）。
  `app/sayings.py::source_url()` 是唯一把「`d,i,k,h` 还是 `https://…`」翻译成
  「该请求哪个地址」的地方：设置页只负责存那串原文、`public_view()` 只负责回显，
  `Sayings.fetch()` 每次现调 `source_url()`（所以改了来源不用重启）。同一串字在第二个
  地方再解析一遍，就会长出「设置里显示 d,i,k,h、实际按别的分类取」这种查不出来的错。
  那 11 个字母的清单同理：权威只有 `app/sayings.py::CATEGORIES` 一份，设置页那行注释
  （`#sSayingsCats`）显示的就是服务端给的 `sayings_categories` —— 2026-10-10 用户要求
  「把一言来源的字母分类注释到『一言来源』后面」，它就从帮助里挪到了输入框下面。
- **一言的多分类要写成重复的 `c=`，官方文档那个逗号写法是 400**。用户给的是
  `https://v1.hitokoto.cn/?c=d,i,k,h`，真机照抄回来的是
  `{"status":400,"message":"很抱歉，没有分类有句子符合长度区间。"}` —— `?c=d%2Ci%2Ck%2Ch`
  和 `?c=d,i` 也一样；`?c=d`（单类）和不带参数都正常。能用的是
  **`?c=d&c=i&c=k&c=h`**：连打 10 次拿到 `{k:2, i:3, d:2, h:2}`（中间一次读超时）。
  所以「把用户给的网址原样填进代码」在这件事上恰好是错的 —— 网址本身要当成**需求**
  读，能让它真出句子才是对的（探针 `_probe_raw.sh` 里那两组写法就是为此留的）。

**自定义口令、外网域名、访问秘钥（2026-10-09 加的四件事，当天改过四次）**

- **地址只能有一份实现**。`settings.front_url()` 是全项目唯一算地址的地方（域名优先，
  其次 `web.public_host`，最后回退到传入的 host/port）。`/日历` 当初被删，就是因为它
  **自己拼**了一个写死的 `http://<你的NAS地址>:8080/` —— 同一个地址有两个实现，
  就一定会有一个是错的。
- **提示页不能把口令印出来 —— 更好的做法是干脆别承认有口令这回事**。`_NEED_TOKEN_HTML`
  原来直接把 `http://{host}/?token={token}` 明文印给**任何**访客，第二步改成只给一个
  `?token=你的口令` 的模板，但页面上仍写着「登录在 config.json 的 web.token /
  settings 表的 web_token 里」—— 等于告诉每个看得见的人「有这么一道门、钥匙在哪儿」。
  用户 2026-10-09 一句话把它整个废掉：「设置访问口令以后，这个页面要伪装成秘钥进入」。
  现在没有这张页面了，`_need_token_page()` 直接回**同一份** `_LOGIN_HTML`。
  **教训**：一道门只要被人看见，就已经泄露了一半；「我告诉你这里有个门，但我不告诉你
  钥匙」这种设计不如「你看不出这里有门」。
- **伪装页必须真的能进去，否则是给人添堵**。共用一张 HTML 只是第一步：口令页那张表单
  提交时**没有 `?token=`**（浏览器本来就是没带对口令才看见它的），所以 `/api/login`
  必须排在 `_check_auth` **前面**，否则主人自己都永远进不去。
- **「伪装」不等于「放行」**（2026-10-09 返工，本块最大的一次理解偏差）。第一版把那张
  假页面做成「框里认秘钥；秘钥登录没开时认口令本身；两个都开时口令也认」—— 也就是
  **填对了真能进去**。用户当场否掉：「如果开了口令，那个不带口令进的登录页就是假的，
  填正确的秘钥也不能通过，不能放行」；接着要求「先不要改，把你理解的告诉我」，助手
  复述了两张页面的区别，他逐条确认「①假页面什么都不认、纯粹是个看得到进不去的门；
  ②算一次错误计数；③外观上一模一样」。**教训**：助手把「让主人不被自己的口令关在
  外面」当成了目标，而用户要的是「这道门对不知道口令的人**没有任何**可用之处」——
  假页面唯一的功能就是**消耗猜的人**。顺手给出去的那条方便路（填对口令就能进），正是
  用户要堵的：口令那层白设了。**碰到「伪装」这类需求，先把两张页面的行为列成表让对方
  确认，再动代码** —— 这一版把语义写反了却一路测过、部署、真机验完才发现。
- **口令页绝不能种口令 cookie**（`_login_page(plant_token=False)`）。顺手种它是很自然的
  写法（登录页本来就种），但在口令那道门上种，等于「没带口令的人来一次就拿到口令」，
  这道门当场消失。补种只能发生在 `_api_login` 成功之后 —— 那一趟才证明对方知道钥匙。
  假页面那条路上**连成功路径都没有**，自然也不会种。
- **`GET /` 会连种两个 cookie，`dict(resp.headers)` 只留得下第一个**。真机上第一版探针
  就是被这个骗了（以为没种设备号）。同上一条：测试侧 `_headers()` 要拼 `get_all`。
- **禁令跟着「还有没有门」走，不是跟着某一个开关走**。`_login_gate` 第一版写的是
  `if not self._login_required(): return True`，也就是「秘钥登录没开就不必判禁」——
  可用户要的禁令恰恰是挂在**口令那层**的伪装页上的（他先设口令，那张页面才开始装成
  秘钥页，也才开始有人来猜）。只开口令的机器上，猜两次照样要停下来等 24 小时
  （`_door_open()`：两层任一在拦人，禁令就算数）。相应地，「自救」也从「关掉秘钥开关」
  变成「**两层都关掉**」（或者重启容器清掉内存里那笔账）—— 只关一层是不够的。
- **`front_url()` 得有 `token=` 形参**。`main._display_url` 手里已经攥着 `config.json`
  那个部署时生成的 token，而它调 `front_url` 的目的就是「把同一个口令印出来」；
  不让它传的话，没有 `settings` 表的单测里会算出一个没口令的地址。
- **`_truthy()` 要自己写**。Python 里字符串 `"0"` 是**真**的，所以
  `if values.get("domain_enabled"):` 会把「关」当成「开」。`web._truthy` 认
  `""/0/false/no/off` 为假。
- **cookie 里的口令必须 `quote()`**。原来是裸 f-string 拼 `Set-Cookie`，自定义口令里
  只要有一个 `;` 或 `&`，整个 Cookie 头就被拼坏了（读的那侧也得 `unquote`）。
- **改秘钥不用清会话**。会话值就是 `sha256(盐|秘钥|版本号)` 的前 32 位 —— 秘钥一变，
  所有旧 cookie 自动失效。**没有会话表**，也就没有「会话表和秘钥不同步」这类 bug，
  也不需要往数据库里写一堆过期时间。
- **但「退出登录」非清会话不可**。本块真机上抓到的：`POST /api/logout` 回了 200、
  `Set-Cookie: woolbot_login=; Max-Age=0` 也发出去了，可**拿同一个旧 cookie 再打
  `/api/calendar` 仍然是 200**。因为会话值不含时间也不含随机数，光让浏览器忘掉 cookie
  拦不住已经抄走它的人。修法是加一个全库的**会话版本号**（`settings.login_epoch()`）：
  退出时 +1，所有旧会话一起失效（`login_epoch` 故意不放进 `ALL_KEYS` —— 它不是给人填的
  设置，是内部记账，只能由 `bump_login_epoch()` 改；坏值当 0，别让一行脏数据锁死所有人）。
  代价是「退出登录」= 所有设备一起退，这正是它本来该有的意思。
- **登录失败保护必须真能累加**。本块真踩到：`_login_record_fail` 里写的是
  `if until <= now: count = 0`，而「还没锁过」时 `until` 初值就是 `0` —— 于是**每次
  失败都先清零再 +1**，计数永远停在 1，`LOGIN_MAX_FAILS` 根本到不了，限流写了等于
  没写。要写成 `if until and until <= now:`（0 表示没锁过，不能当过期处理）。
  这种错不报错、不影响正常登录，只有字典攻击时才看得出来。
  上限从 5 改成 **2** 也是用户定的：伪装页上线后「谁都能试」成了常态，5 次太宽容。
- **「同一台设备」得先有设备号**。要做「同一 IP **或**同一设备」二选一就封，设备号只能
  靠 cookie 认；而**头一次来就 POST 的客户端没有设备 cookie**。这时如果照样记一条
  `dev:` 空号码的账，所有这样的人会共用一笔账 —— 一个人错两次，全网第一次来的人都
  被关 24 小时。所以 `_login_fail_keys()` 是「永远记 IP，**只在已经带了设备 cookie
  时才追加设备那条**」；登录页 `GET` 时就顺手种一个（`secrets.token_hex(16)`），
  正常人第二次请求就带着它了。
- **一次响应发两个 cookie 只能发两个 `Set-Cookie` 头**，而 `_send()` 原本只接受一个
  `extra` 字符串。改成「值是 list/tuple 就 `send_header` 发多次」。测试侧也跟着踩了一个：
  `dict(resp.headers)` 会把**重复的 `Set-Cookie` 丢掉、只留第一条** —— 表现为
  「明明发了设备 cookie，测试总说没种上」。`tests/test_web.py` 的 `WebApiTestBase._headers()`
  现在把 `get_all("Set-Cookie")` 拼成一条，用的人再按 `", "` 拆（**不能直接 `split(";")`**，
  那样第二条 cookie 的名字会和第一条的 `HttpOnly` 粘在一起）。
- **「禁止访问」是整站，不是只锁登录按钮**。用户 2026-10-09 的原话是「禁止访问 24 小时」，
  所以要给接口回 403 而不是 401（401 会让前端去要登录页，等于还有机会继续试），
  页面直接换成一张没有表单的「🚫 暂时不许访问」。**禁令那一步还得排在会话检查前面**
  —— 本块真机探针第一次就是这么漏的：探针手里那个会话在登录那一步已经拿到了有效
  cookie，于是 `/api/calendar`、`/api/settings` 全是 200，看着像「禁令根本没生效」。
  排到前面之后，带有效 cookie 打 `/api/stats`、`/`、`/app.js` 一律 403。
  `/api/health` 必须放行，否则容器永远 unhealthy、部署脚本自己也报错。
- **秘钥不合规要拒绝，不要替人改**。长度或字符种类不达标就 400 并把缺的列出来；
  「悄悄截断/补齐」会让用户以为存的是自己填的那串。前端也**不 trim** —— 空格算符号，
  trim 掉的话「填的一样、存的另一样」这种 bug 只能靠猜。
- **老字段要留着认**。秘钥从 `login_password` 改名成 `login_key`，读取时先查新名字、
  没有再回落到老名字（`login_key()`），登录接口也仍然认 `password` 字段 ——
  老书签、老脚本、已经部署过的 NAS 不该因为一次改名全部失效。
- **表单登录成功要回 303，不能回 302**。302 保留 POST 语义，浏览器刷新页面会弹
  「要不要重新提交表单」；303 明确说「去 GET 那个地址」。`Set-Cookie` 要挂在**这个
  303 响应**上。测试里注意：`_NoRedirect` 会把 303 变成 `urllib.error.HTTPError`，
  那不是失败，正是成功的样子（别在 `except` 里直接 `self.fail`）。
- **`urllib` 默认自己跟着重定向走**，跟过去就变成一次没 cookie 的 `GET /` → 401 口令页，
  看着像「登录接口坏了」。测表单登录要用一个 `redirect_request` 返回 `None` 的 opener
  （`tests/test_web.py` 里的 `_NoRedirect`）。
- **`login_ready()` 要两个条件都齐**（开关 + 秘钥）。只看开关的话，「开了登录
  还没填秘钥」这个中间状态既把人锁在外面、又没有任何防护 —— 两头不落好。
  用户名 2026-10-09 去掉了，所以条件从三个变成两个。
- **`web_token` / `login_key` 不能放进 `FLAG_KEYS`**。`settings.update()` 对
  `FLAG_KEYS` 里的键会把值写成 `"1"/"0"`，口令会被写成 `"1"`。
- **设置弹窗里多一个 `class="dim"` 就会挂**。`SettingsSheetTest` 数着这个类名
  （必须正好 2 个），加控件时用 `<label>` 而不是 `<p class="dim">`。

  `id="helpModal"`，只覆盖弹窗**里面** —— 顶栏那些控件得单独断言（拿
  `<div class="top-right">` 到 `</header>` 那一段切）。
- **「退出」从顶栏挪进了设置弹窗**（2026-10-09，用户 m04278：「我一点设置这里就会

**重复规则（每天 / 每周 / 每月）和「每周几次、每月几次」**

- **一行只能有一个 `grab_at`，而「每天」是一条线**。这是整个功能的症结：活动表是
  按「一次性事件」设计的，加重复之后，`list_range(d, d)` 按 `grab_at` 查，一张
  「每天 09:00」的券在 3 天后那一天**一条都查不到** —— 用户看到的就是「日历上有、
  问机器人却说没有活动记录」。修法是 `db._repeat_rows_between()` 把重复行并进
  `list_range()`，SQL 只粗筛「系列已开始且未结束」，精确判断仍调 `repeat.py`。
- **同一套规则绝不要有两个实现**。日历和机器人各算一遍「哪天算开抢」，两者分叉过
  一次，结果就是日历画 10月7日、机器人答 10月8日（用户拿红笔在截图上画了一圈
  「?」）。现在 `app/repeat.py` 是唯一权威，前端**不自己算** —— 接口直接给
  `occurrences`。配额那部分同理：机器人清单里的「（本周 1/2）」和日历卡片上的进度
  都调 `repeat.quota_state`，谁也不许自己数。
- **`CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做**。用户库里已经有真数据，
  不能重建表，所以新列走 `db._migrate()` 的 `ALTER TABLE ... ADD COLUMN`（用
  `PRAGMA table_info(activity)` 查缺哪列）。`activity_done` 是**新表**，才走
  `CREATE TABLE IF NOT EXISTS`。
- 接口上的「重复」有三个不同的意思，必须分开：**没提这个键** = 不动已存的规则；
  **空串** = 明确清空、退回一次性；**认不出的字符串** = 回 400。绝不能默默存成
  一次性 —— 用户明明写了「每天」却没生效，是这类功能里最难发现的一种错。
- **排期和配额不能塞进同一个字段**。`repeat` 那句话是**要重新解析的**：把
  `describe()` 的输出（「🔁 每天 09:00 · 周限2次」）原样填回编辑框，用户再存一次
  就会连配额一起被解析器重写。所以列表接口另外给 `repeat_input`（只有排期那句），
  配额走 `quota_week` / `quota_month` 两个数字，编辑框也分成三格。
- **改编辑框时「认不出的配额」绝不能写成空**。用户只把「每天 09:00」改成
  「每天 09:30」，备注里并没有「每周几次」，若照 `fields_from()` 的结果整片覆盖，
  箱子里填着的 `quota_week=2` 就被抹了。`web._merge_repeat()` 因此只写**认得出的**
  配额列（新建走 `replace=True` 照写）；要清空得显式发空串。唯一的例外是整条
  **退回一次性**：那时候配额跟着排期一起清。
- **补老数据时「只补配额」和「`--all` 重判」是两条路**。放宽 `rows_needing_repeat()`
  去捞「有排期但没配额」的老行之后，如果重读原文时顺手把排期也重写，`--all` 才该有
  的行为就漏进了默认路径 —— `test_backfill_all_rejudges_a_row_that_already_has_a_rule`
  当场抓到（那行会从周三被改成周五，而用户没要求重判）。`cmd_backfill_repeat` 现在按
  `redo` 分支：不带 `--all` 时对已有规则的行**只写配额列**。
- 确认环节（`__confirm__:对`）容易被漏掉：那一步模型只被问「对不对」，很可能不回声
  `repeat`，于是规则在用户说「对」的那一刻凭空消失。`_resolve_pending` 现在按标题
  从待确认的 payload 里把那几列补回来 —— 用 `rp.FIELDS` 循环，**别写死列名**，
  加列的时候一定会漏。
- `describe()` 里那个范围连接符是 **en-dash（`–`，U+2013）**，不是 ASCII 的 `-`。
  写断言时直接复制输出，别手打。
- **「每周三档」「每周一次」里的数字不是星期几，是量词**。第一次回填就把用户那条券
  认成了周三：备注里「每人每周三**档**力度乐园门票消费券」排在「每周五中午12:00开始
  发放」前面，而 `search()` 只取第一个匹配。现在 `_weekly_days()` 会躲开后接量词
  （档种类款张次…）的匹配，并优先选「后面紧跟时刻」的那个。`parse_quota()` 同样
  **不认「档」**（那是力度档位不是次数），只认次/张/份/个/件/笔/单/回。
  **别小看这一步：规则认错不会报错，只会在日历上安静地少显示几天。**
- **「每周日10点」里的 `10` 不是星期一**。一个正则抓多个星期几之后，绝不能顺手把
  阿拉伯数字也当成星期几（`1`→周一），否则「每周日10点」会变成「每周日、周一」。
  所以 `_WEEKLY_RE` 只认中文数字（一~六、日、天）；`_MONTHLY_RE` 反过来**必须**带
  「日/号」兜底，免得把「每月1次」当成 1 号。
- **列表里每一项可以各自带一遍「周/星期/礼拜」**（2026-10-10，用户报的「重新发截图
  录入，clawbot 说已记下，前端却看不到」）。真原文是「一、领券时间：2026年8月22日至
  2026年12月31日，**每周六、周日**09:00:00至23:59:59」（#80 建行银联商圈满1000减116
  元券），老写法只吃「每周二、四」「每周一三五」这种**只在开头写一次**的列表，于是
  `repeat_days` 只存下 `"5"`，周日那一场永远不显示 —— 而回执、编辑框都照实说
  「每周六」，用户根本看不出少了半天。现在 `_WEEK_PREFIX` 在列表的每一项前都可选，
  `_parse_week_run()` 本来就是逐字映射、会跳过「周」这类无关字，所以认得
  「每周六、周日」「每周六和星期日」「每周二、星期四」，老写法一个都没动。
- **重复系列的起点取 `start_at` 与 `grab_at` 里早的那个**（同一天同一件事）。`grab_at`
  只是模型给的「**下一次**开抢」：那张 #80 的 `grab_at` 是周日 10-11（10-11 确实是
  周日，符合规则），可 `occurrence_on()` 原来拿 `grab_at` 当门槛，于是「今天（周六
  10-10）那一场」被一句「系列还没开始」吃掉 —— 日历上今天什么都没有，用户看到的就是
  「明明说已记下，却看不到」。`_series_start()` 现在两块时间取早的（`start_at` 才是
  活动真正开始的那天），`_anchor_of()` 保持原样只给「没写星期几/几号时猜一个」用。
  **教训：凡是「从哪天算起」和「下一次是哪天」两件事，别用同一个变量。**
- **显示对了不代表存下来了**。2026-10-10 把全库 31 条审了一遍，发现 **14 条 weekly 行的
  `repeat_days` 是空的** —— 它们的「每周五」只是 `describe()` / `rule_of()` 拿 `grab_at`
  那个锚点**猜**出来的，日历、清单、编辑框里一切正常，谁也看不出来。危险在于：这种行
  哪天动了开抢时刻（编辑、重录、`--all` 重判），猜出来的星期几就跟着变，规则会在用户
  没要求的情况下被改掉。现在这 14 条的星期几都显式写进列里了（`0`＝周一 … `5`＝周六
  `6`＝周日）；同一次审计里唯一「新解析器判得不一样」的是 **#41 浦发「66生活」周六1元购**：
  它备注里那句「每日活动时段约10:00-17:00」会被认成「每天」，但用户拍板它就是**每周六**，
  所以保持原样。**教训：能被解析器认出来的规则就落到列里，别留一个靠锚点猜的空列。**
- **行级的 `status` 对重复活动只有一个意思：`expired`**。一格 status 装不下几十场，
  用户以前误点过一次「标记完成」，整条就再也不是「待抢」了。现在「这一天领到了」
  记在台账表 `activity_done(activity_id, day)` 里（主键就是这两列，`INSERT OR IGNORE`
  天然幂等），`occurrence_status()` 忽略行级 `done`；配额满导致的那张「已完成」也是
  算出来的，不是存下来的。页面上按钮相应成了「标记**本次**完成 / 撤销本次」。
- **删活动要连台账一起删**。`activity_done` 里留下的孤儿行会让「本周已经领了几次」
  虚高 —— `delete_activity()` 里那句 `DELETE FROM activity_done` 和删活动在同一个
  事务里。
- **「没有开始时间」时，唯一能证明它已经开始的就是开抢时刻已经过去**。`claimable_on()`
   原来只判 `end_at >= 今天`，于是「后天才开抢、后天就截止」的券在今天被说成
   「还能领的」；日历那一天的面板里真的多摆了一张卡，上面还写着「🎯 10:00 开抢」
   （在 10月6日 的面板里会被读成今天 10:00）。
- **`db.list_range()` 只认 `start_at`** 时，模型只给 `grab_at` 的长效券（「每天 08:30
   起发放」这类经常只有开抢时刻）会对**每一天**隐身：机器人答「没有活动记录」，可它
   明明还能领。现在第二支还认「开抢已过 + 有有效期」，但**必须要求 `end_at` 存在** ——
   否则没写有效期的老券会被当成「永远有效」，出现在自己开抢之后的每一天里。

**自然语言删除**

- **空对象在 JS 里是真值**。后端「没有失败」时曾经回 `last_error: {}`，前端写的是
  `data.configured && data.last_error` —— 于是模型好好的，页面顶部却一直挂着
  「⚠️ AI 模型用不了」，偏偏旁边的弹层里正显示「✅ 通了」。修了两头：后端没失败时
  回 `null`，前端再上一道 `hasError()`（**判据落在「这条记录里有没有内容」，不是
  对象真假**）。任何「可能给空对象」的接口都得这么防一手。
- **删除绝不能在用户确认前发生**。`_handle_delete` 只做检索 + 列编号（最多 10 条，
  并告诉你库里还有几条没列出来），把 `{ids, titles, keyword}` 存进 `pending`；
  真正落刀在 `_resolve_delete`。编号越界时**不做任何猜测**，而是把 pending 存回去
  再问一遍 —— 猜错的代价是不可逆的。没有 `user_id`（没地方存待确认）时干脆什么
  都不做。
- **别让模型拥有删除能力**。提示词里必须写明「你没有删除能力，只抽关键词」，
  否则它会开始输出「应该删掉第 1、3 条」，而那等于让模型对着一个它看不见的库瞎指。
- **动词兜底只抢 `other` / `query` 两类意图**：「明天9点京东抢券，把旧那条删了」
  里也有「删了」，但这句话的重点是**记下来**；模型认成 `ingest` 时不能被兜底抢道。

**工程**

- **绝不要对提示词调 `str.format()`**。提示词里嵌着 JSON 示例，`format` 会把示例的
  大括号当成格式字段：`UNDERSTAND_PROMPT.format(anchor=...)` 抛
  `KeyError: '\n  "intent"'`，于是 `understand()` **每次调用都异常**，录入和查询
  全废 —— 而且桩掉 LLM 的单元测试完全看不见，一路活到了部署之后。现在统一走
  `app/llm.py` 的 `_fill()`（单趟正则、只认 `[a-z_]+` 字段名、认不出的原样留着）。
- Windows 控制台默认 GBK，`print` 里的 emoji 会抛 `UnicodeEncodeError` —— 入口
  和工具脚本都调了 `stream.reconfigure(encoding="utf-8")`。
- CSS 里 `.modal { display: flex }` 会盖掉浏览器默认的 `[hidden] { display: none }`
  （作者样式表优先于 UA 样式表），弹层会永远显示。带 `display` 的元素必须显式写
  `.xxx[hidden] { display: none }`。设置弹窗里那三个小页同理：`.sheet .sheet-pane` 是
  `display: flex`（它得跟 `.sheet` 一样按列排、间距一致），所以紧跟一行
  `.sheet .sheet-pane[hidden] { display: none }` —— 少了它，三页会一起摊在弹窗里，
  而翻页的 JS 看着一切正常。
- **同一个作用域里声明两次同名函数，JS 不报错，只是后者把前者顶掉**。2026-10-07
  加详情里的时间格式时，新写的 `fmtDay(day)`（接 ISO 字符串）把老早那个
  `fmtDay(date)`（接 Date 对象，`visibleRange()` 靠它拼查询区间）顶掉了 —— 于是
  页面去请求 `/api/activities?from=NaN月NaN日`，**整个月视图白屏**，而那时六套测试
  全绿（静态断言只看「关键名字在不在」，没人跑真浏览器）。现在
  `tests/test_web.py::test_no_two_top_level_names_in_the_page_script` 直接查
  `app.js` 顶层重名；同理 Python 那边 `_CN_DIGITS` 也被同一类坑咬过（见查询口径那节）。
- 表单里不要给字段起 `title` / `action` 这类名字，会和 `HTMLFormElement` 自带的
  属性打架；统一走 `form.elements.xxx`。
- **删掉一个 DOM 节点，必须一起删掉渲染它的那个函数**。2026-10-07 把月视图改成
  「左日历 + 右清单」时，`index.html` 里的 `#dayPanel` 整块拿掉了，`app.js` 的
  `renderDayPanel()` 也跟着删 —— 留着它不报错（元素找不着就 `null` 崩在别处），
  但代码里会永远留着一份「当日面板」的说法，下次改版谁也说不清哪个才是真的。
  `tests/test_web.py::test_the_month_view_is_a_calendar_beside_a_list` 现在把
  `sidePane`/`sideHead`/`sideBody` 钉住、并反向断言 `dayPanel`/`dayList`/`dayTitle`
  **不存在**。
- **生成表的那段代码里，相邻的字符串字面量会静默粘在一起**。`tools/build_lunar_tables.py`
  一开始把二十四节气的名字按行拼进 `_lunar_tables.py`，某一行末尾少了个空格，于是
  Python 的隐式拼接把「春分」和「清明」粘成了「春分清明」—— 结果 `TERM_NAMES` 只有
  21 项，查节气时 `IndexError`。生成器写文件时每个名字后面补一个空格最省事；另外
  「生成的表一定是 24 项的整数倍」这类不变量，值得在生成后立刻断言一次。
- `timeutil` 的时间戳换算走 `from_timestamp()`：容器里系统时区是 UTC，日志会全变成
  UTC，排时间问题要多一次心算。
- 本机有**两个 Python**，别搞混：`C:\Program Files\python\python.exe` 是 **3.8.6**
  （paramiko / requests 在这里，`deploy/nas_key.py`、`deploy/deploy_woolbot.py` 用它），
  `%LOCALAPPDATA%\Programs\Python\Python312\python.exe` 是 **3.12.9**（本项目用它）。
- 用完的临时文件不必留在仓库里：`data/`、`config.json`、`.env`、`.preview/`、
  `.chrome*/`、`tests/.tmp/` 都在 `.gitignore` 里。
- 测试里**不要用 `tempfile.mkdtemp()`**：本机沙箱下它建出来的目录不可写，连
  `O_CREAT` 都 `Permission denied`，sqlite 会报 `unable to open database file`。
  统一用 `tests/.tmp/<名字>-<pid>-<随机>` 自己 `mkdir`。
- 测试里拼 URL 记得编码非 ASCII 参数（`urllib.parse.quote`），否则带中文的查询
  参数在 `urllib` 那一层就炸了，看起来像接口坏了。
- **自检不能只看 `config.json`**。`main.py check` 早先判的是
  `if not provider.get("api_key")`，而网页上配的 key 存在 SQLite 的 `settings` 表里、
  由 `app/llm.py::_refresh()` 在**每次调用时**盖到 provider 上 —— 于是「在网页上配好的」
  实例（就是线上这台：`/api/settings` 明明 `configured: true`）自检会红着脸说
  「❌ 没有 api_key，机器人无法调用模型」并退 1。**自检必须问「真正在用的那把 key」**，
  现在统一走 `LLM(provider).configured`，输出里还会写明 key 是页面填的还是 config 给的。
  同类风险：任何「绕过运行时那一层、直接读原始配置」的判断都可能是假故障。
- **容器的 DNS 别继承宿主 —— 它只在启动那一刻看一眼，之后再也不看**。2026-10-08
  真机上模型和一言同时报
  `HTTPSConnectionPool(host='api.deepseek.com', port=443): Failed to resolve 'api.deepseek.com'
  ([Errno -3] Temporary failure in name resolution)`。看着像 key 失效或余额用光，
  其实是 DNS：NAS 上装着 Tailscale，它会把宿主的 `/etc/resolv.conf` 换成自己的
  MagicDNS（`100.100.100.100`）。容器**启动那一刻**若正是它，Docker 就把这个上游
  记进容器内 `127.0.0.11` 转发器的 ExtServers（`docker exec woolbot cat /etc/resolv.conf`
  的注释里能看到），**运行期间不会重读宿主**。之后 Tailscale 一断（回到家里、
  或者服务停了），容器里所有域名解析立刻全灭 —— 而 `docker run --network host` 的
  容器同一时刻解析正常，宿主 `curl` 也正常，特别容易误判成「机器人的网络坏了」。
  诊断顺序：`docker exec woolbot cat /etc/resolv.conf | grep ExtServers` →
  `docker exec woolbot python -c "import socket;print(socket.gethostbyname('api.deepseek.com'))"`；
  临时解法 `docker restart woolbot`，**根治要写死 DNS**（`docker-compose.yml` 里的
  `dns: [223.5.5.5, 1.1.1.1]`，可用 `WOOLBOT_DNS` / `WOOLBOT_DNS_BACKUP` 覆盖），
  这样与 Tailscale、路由器的状态彻底解耦。

**启动日志里的口令、以及容器端口 8080 → 16886（2026-10-10，用户原话「改，然后再把容器
端口8080修改为成16886」）**

- **日志里的口令必须现读设置，不能读 `config.json`**。`main.py` 里两处（`cmd_web` 与
  all-in-one）都写成 `token = (cfg.get("web") or {}).get("token") or ""`，而
  `settings.front_url()` 的签名允许调用方**把口令传进来**（传了就不再读设置）—— 于是
  用户在页面「设置」里改过口令之后，**同一个进程的启动日志印出两个不同的 token**：

  ```
  INFO woolbot.web: 日历页面已启动：https://calendar.example.com:5668/?token=你的页面口令
  🗓  日历页面（也是扫码的地方）：https://calendar.example.com:5668/?token=你的页面口令
  ```

  第一行（`web.py` 那行，不传 token）是对的，第二行（`main.py`，传了 `config.json`
  里部署时生成的那把）是个**废 token，谁点谁进不去**。现在两处都传 `st.web_token(cfg)`
  （= 设置里生效的那把）。**教训**：「同一个东西有两个来源」的 bug 不会报错，它只会
  让两行日志互相矛盾 —— 真机上就是靠这两行不一样才发现的。
  `tests/test_main.py::StartupTokenTest` 里有一条源码级断言盯着这两处别再改回去。
- **端口这件事有四个地方各写了一遍**（`app/config.py::DEFAULT_WEB_PORT`、
  `docker-compose.yml` 的映射两侧、`Dockerfile` 的 `EXPOSE`、`config.example.json`），
  漏一处就是「页面打不开」或者「容器一直 unhealthy」。现在默认值只有
  `DEFAULT_WEB_PORT` 一个来源，其余三处引用它或跟它对齐，并由
  `tests/test_main.py::DeploymentPortTest` 盯着。`Dockerfile` 的健康检查改成
  **现读 `config.json` 里的端口**：写死一个数字在这儿，改了端口它就会一直报
  unhealthy，而页面明明是好的 —— 这种「假故障」最费时间（同一条教训见上面那条
  「自检不能只看 `config.json`」，方向正好相反：**该现读的地方别抄快照**）。
- **端口改了，NAS 上那层反代不会自己跟着改**。`calendar.example.com:5668` 是 **Lucky**
  转进来的（`/vol1/@appcenter/Lucky/bin/lucky`，面板 `http://<NAS>:16601`），
  它的规则文件是 root 权限、`普通用户` 读不到，所以助手改不了 —— 只能人工去面板里把目标
  端口改成新端口。**改容器端口前先想清楚这一层**：局域网地址改了没什么，外网地址会
  直接 502（而且那时候很可能已经不是 8080 了，见上一节「端口」里的实测）。
- **`deploy/deploy_woolbot.py` 会把端口写进 NAS 的 `config.json`**（`web.port` =
  `DEFAULT_WEB_PORT`，`web.public_port` = `--local-port`，默认同一个号），并且**在上传
  之前**就核对 `docker-compose.yml` 里有没有 `{local-port}:{容器端口}` 这个映射，
  对不上直接退 2 —— 这种错等部署完再发现，代价是「页面白屏 + 容器 unhealthy」。
  它最后印的那条「🗓 日历页面」链接也不再用 `config.json` 里那把口令，而是
  `docker exec` 进容器**直接读 settings 表**（读不到才退回 config.json 的值并加一句
  「已经作废」）—— 同一个「日志印废 token」的坑，踩过一次就够了。
  **顺带一条静默陷阱**：`docker exec woolbot python -c "from app import settings as st;
  print(st.web_token())"` 这种一行命令拿到的是**空串**（新进程没有 `db.init()`，
  `_load()` 失败后按空处理并只在 stderr 抱怨一句），它**不会**退回去读 `config.json`，
  所以想在外面问「现在生效的口令是哪把」就得读 settings 表（`select value from
  settings where key='web_token'`），或者带上 `cfg`。

  那一发 `-14` 是我们自己清 token 造成的，不是账号被暂停，替它守灵一小时毫无道理；④
  `run()` 一进「未登录」分支就 `_logout.clear()`，否则新码扫完了长轮询第一件事就是收工，
  表现成「扫码成功但机器人装死」。盯它的三条在 `test_wechat.py`：

  不崩、**两个动作各占一个槽位不会互相挤掉**）；页面上那句确认框**必须**写明「微信里那条
  授权还在，想彻底解绑请到微信里『解除连接』」（`test_core.py` 断言 `解除连接` 四个字还在
  `app.js` 里），否则用户会以为点了它就等于解绑了。
